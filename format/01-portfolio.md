# 기준 ① 포트폴리오 (포트폴리오 문서 · 발표 덱 · 상세 기술문서)

> 원본: 「유니티 개발자 취업·기술 문서 작성 가이드 v2」 **Part 1 §3 포트폴리오**
> (https://koohoo-dev.github.io/portfolio-guide/guide.html#1)
> 이 파일은 Claude가 포트폴리오 페이지를 만들고 점검할 때 쓰는 **판정 기준 압축본**입니다.

프로그래머 역량을 **실제 구현물로 증명하는 가장 핵심 문서**입니다.
"할 줄 안다"는 주장이 아니라 **한 결과물**을 보여줍니다.

포트폴리오 = **① 요약 문서** + **② 시연 영상** + **③ 프로젝트 상세 문서**(기술 문서).
시연 영상과 기술 문서는 **짝을 이뤄** 보여줄 때 효과적입니다. 이 템플릿은 이것을 **세 페이지**로 그립니다.

| 페이지 | 주소 | 무엇 | 바탕 |
|---|---|---|---|
| **포트폴리오 문서** | `index.html` | ① 요약 문서. 아래로 읽는 한 페이지, A4 인쇄로 **제출용 PDF**가 되는 페이지 | `data/portfolio.json` + `data/projects/*.json` |
| **발표 덱** | `project.html?p=<폴더 이름>` | ③ 상세 문서를 바탕으로 한 16:9 발표 슬라이드. 다이어그램·화면·표·코드가 주인공 | `data/projects/<폴더>.json`의 `deck` + 기술 문서 md의 원문 블록 |
| **상세 기술문서** | `doc.html?p=<폴더 이름>` | ③ 기술 문서 **전문**을 그대로 그림 (읽는 문서형, A4 인쇄) | `src/<폴더>/기술문서.md` |

> 세 문서의 역할은 다릅니다. **한 파일(PDF)로 묶더라도 장을 나눠, 역할을 섞지 마세요.**
> 포트폴리오 문서·발표 덱에 새 내용을 쓰지 않습니다 — 기술 문서에 쓴 것을 보여줍니다 (`CLAUDE.md` 원칙 1 "지어내지 않는다").

## 1. 포트폴리오 요약 문서 → 포트폴리오 문서 `index.html`

리크루터가 **빠르게 파악**할 수 있도록, 기술 기반 성과 중심으로 구성합니다.
절: 머리(이름·연락처) → 자기소개 → 기술 스택 → 프로젝트마다 2절(**소개** · **기능 소개**) → 한눈에 보기 → 연락처.
인쇄(A4)하면 머리·자기소개·기술 스택이 맨 앞(기술이 많으면 2쪽까지), 프로젝트마다 소개와 기능 소개가 각각 새 쪽에서 시작, 한눈에 보기·연락처가 맨 끝입니다.

| 항목 | 작성 지침 | 데이터 위치 |
|---|---|---|
| 이름 / 연락처 | 상단에 명시 | `profile` |
| 기술 스택 요약 | **단순 나열 금지.** 경험 기반 (예: "Unity — FSM 전투 시스템 설계") | `skills[]` |
| 대표 프로젝트 | 제목 + 한 줄 설명 + 기술 키워드 + 본인 역할 | `projects/*.json` (`title`·`tagline`·`tags`·`team.role`) |
| 프로젝트 소개 | 큰 대표 이미지 + 장르·기간·인원·환경 격자 + **개발 의도** + 태그 + 링크(인쇄에서는 칠 수 있는 주소) | `cover`, `meta`, `intent`, `links`, `tags` |
| 기능 소개 | 화면은 왼쪽에 모으고, FEATURE 번호 + 제목 + 설명과 [발표 덱에서 보기]는 오른쪽 목록. **2~4개** | `highlights[]` (`image`는 그 기능 절에 실제로 있는 이미지만) |
| 협업 경험 | 팀 프로젝트라면 **기여도·역할을 반드시 분리** 명시 | `team`, `role` |
| 링크 정리 | GitHub · 기술 문서 · 시연 영상 바로가기 | `links` |

**한눈에 보기** (프로젝트 요약, 자동 생성)

| 프로젝트명 | 한 줄 소개 | 핵심 기술 | 역할 | 링크 |
|---|---|---|---|---|
| 디펜스 게임 | 실시간 멀티 디펜스 | Unity, Fusion, FSM | 팀 리더 / 네트워크 | GitHub · 기술문서 · 영상 |

### 두 가지 구성 방식 (`profile.md`의 `구성 방식`)

| 방식 | 구성 | 적합한 경우 |
|---|---|---|
| **프로젝트 중심** (`project`) | 자기소개 → 기술 스택 → 프로젝트 1·2·3 | 완성 프로젝트가 여러 개일 때 |
| **기술 스택 중심** (`stack`) | 자기소개 → 기술 스택별로 관련 프로젝트 연결 | 특정 기술 전문성을 강조할 때 |

### 기술 스택: 경험 기반으로

| 👎 아쉬운 예 | 👍 좋은 예 |
|---|---|
| Unity, C#, Git, Photon | **Unity** — 이벤트 기반 크래프팅 시스템 설계, 확률 판정을 주입해 테스트 (CraftingSystem) |
| "숙련도 상/중/하" 막대 | 실제로 **무엇을 만들었는지** + **어느 프로젝트에서** |

→ 기술마다 **근거 프로젝트**가 최소 1개 있어야 합니다. 근거 없는 기술은 싣지 않습니다.

## 2. 프로젝트 상세 문서 → 상세 기술문서 `doc.html?p=<폴더 이름>` · 발표 덱 `project.html?p=<폴더 이름>`

단순 구현 설명이 아니라 **"왜 그렇게 만들었는가", "문제를 어떻게 해결했는가"** 가 핵심입니다.

- **상세 기술문서**(`doc.html`)는 `src/<폴더>/기술문서.md` **전문**을 그대로 그립니다. 글로 읽는 정본입니다.
- **발표 덱**(`project.html`)은 같은 문서를 바탕으로 `/portfolio-build`가 고른 장면 목록(`deck`)대로 그립니다.
  그림·코드·표·화면은 **원문 블록을 가리켜 그대로** 보여주고(옮겨 적지 않음), 장면 글은 짧은 조각(`lead`·`points`)만 둡니다. 원문 그대로가 아닌 조각(`verbatim: false`)은 리포트 "확인해 주세요"에 들어갑니다(원칙 3).
  장면 순서는 원문 장 순서, 한 주제를 "구조 → 흐름 → 구현" 여러 장면으로 나눕니다.

아래 항목은 **기술 문서 안에** 있어야 하는 것이고, "데이터 위치"는 포트폴리오 문서(와 예전 데이터의 자동 구성)가 쓰는 칸입니다.

| 항목 | 설명 | 데이터 위치 |
|---|---|---|
| 프로젝트 이름 / 한 줄 소개 | 명확한 이름 + 어떤 게임·앱인지 핵심 요약 | `title`, `tagline` |
| 개발 환경 | Unity 버전, 외부 패키지, 팀원 수, 기간 | `meta` |
| 주요 기술 / 구현 내용 | 핵심 기술(FSM·네트워크·AI 등) + 구현 방식 요약 | `tags`, `highlights` |
| 링크 모음 | GitHub, 시연 영상, 관리 툴(Notion·Jira 등) | `links` |
| 스크린샷 | 핵심 화면 **4~6장**, 기능이 구분되게 배치 — **기술 문서 안의 이미지 수**로 셉니다 | 원문 이미지(발표 덱 `visuals`) · `screenshots`는 그중 예전 데이터의 자동 구성용 **최대 6장** |
| 구현 콘텐츠 설명 | 각 기능의 구현 의도·방법·**선택 이유**까지 | `highlights`(포트폴리오 문서용 2~4개) · 발표 덱은 `deck.slides` |
| 이슈 해결 사례 | 문제 원인 → 해결 방식 → 결과·회고 순서로 | `troubleshooting`(발표 덱 옛 주소 `ts-n`·자동 구성용 0~3개) · 발표 덱은 문제 해결 장면 |

> `highlights` 2~4개는 **포트폴리오 문서 기능 소개용**, `screenshots` 6장 · `troubleshooting` 0~3개는 **예전 데이터 자동 구성·발표 덱 옛 주소용** 상한입니다.
> 발표 덱은 상한 대신 **장면 수 15~30장**(넘으면 리포트 참고)을 봅니다. 필드 규칙은 `.claude/skills/portfolio-build/schema.md`.

### 구현 콘텐츠 한 항목 (`highlights[]`)

| 항목 | 내용 |
|---|---|
| 콘텐츠명 | 보스 몬스터의 상태 기반 공격 AI |
| 기능 설명 | 체력·거리·쿨타임 조건에 따라 다른 공격을 선택 |
| 구현 방법 | `State Pattern`으로 상태별 클래스 분리, `Animator` 트리거와 연동해 전환 |
| 선택 이유 | 복잡한 조건 분기를 줄이고 유지보수를 쉽게 하려고 상태 패턴 채택 |

- **구현 방법**은 구조·흐름·로직 순으로.
- **선택 이유**는 그 방식의 장점 + 다른 방식과의 비교 + 유지보수·확장성·성능 이점.
  "그냥", "검색해 보니"는 선택 이유가 아닙니다.

### 이슈 해결 사례 (`troubleshooting[]`)

| 항목 | 내용 |
|---|---|
| 이슈 상황 | 보스 공격 시 특정 패턴이 랜덤 반복되어 재미가 떨어짐 |
| 원인 분석 | 공격 조건이 단순 랜덤으로만 구성됨 |
| 해결 방법 | 체력·쿨타임·거리별 **가중치 시스템**을 설계해 상황에 맞는 공격 선택 |
| 결과 | 반복 패턴 감소, 전략적 전투 가능성 증가 |

## 체크리스트 (점검 리포트의 기준)

| 구분 | 체크포인트 | 심각도 |
|---|---|---|
| 포트폴리오 문서 | 이름·연락처·GitHub가 있다 | 필수 |
| 포트폴리오 문서 | 기술 스택이 **경험 기반**이고, 기술마다 근거 프로젝트가 있다 | 필수 |
| 포트폴리오 문서 | 프로젝트마다 한 줄 소개 + 핵심 기술이 있다 | 필수 |
| 포트폴리오 문서 | 팀 프로젝트는 **내 역할·기여 범위**가 분리돼 있다 | 필수 |
| 포트폴리오 문서 | 개인 프로젝트도 담당 범위(직접 만든 것·외부 리소스)가 드러난다 | 참고 |
| 기술 문서 | 개발 환경(엔진 버전·기간·인원)이 있다 | 필수 |
| 기술 문서 | GitHub 링크가 있다 / 시연 영상 링크가 있다 (`#` 같은 자리표시자는 "없음") | 권장 |
| 기술 문서 | 문서 안 이미지가 4~6장이고, 각 장이 서로 다른 기능을 보여준다 | 권장 |
| 기술 문서 | 구현 콘텐츠마다 **선택 이유**가 있다 | 필수 |
| 기술 문서 | 이슈 해결 사례가 1개 이상, 원인→해결→결과 순서다 (결과 = 해결 뒤 달라진 점) | 권장 |
| 발표 덱 | 장면의 그림·코드·표 참조가 원문 **정확히 1곳**으로 풀린다 — 빨간 띠 `visual-missing`(0곳) · `visual-ambiguous`(2곳 이상) · `visual-changed`(원문이 바뀜) · `key-invalid` 0건 | 필수 |
| 발표 덱 | 장면 안 내용이 잘리지 않는다 — 잘림 띠 `clipped` 0건 | 필수 |
| 발표 덱 | 장면 수 15~30장 · 채움률 60% 이상 · 다이어그램 실효 글자 10px 이상 (참고 지표 `many-scenes` · `low-fill` · `tiny-diagram`, 기준 ②·③) | 참고 |
| 공통 | 적혀 있는 URL·이미지 경로가 실제로 동작한다 (대소문자 포함) | 필수 |

> 발표 덱 행은 미리보기에서 `PFScene.report()`로 봅니다 — `audit`(빨간 띠, 배포·PDF에도 보임)과 `info.notes`(참고 지표, 배지 없음).
> 포트폴리오 문서(`index.html`)는 장면이 아니라 흐르는 페이지라 잘림 띠가 없습니다. `PFPage.report()`로 깨진 이미지(`images.broken`)·빠진 프로젝트 절(`sections`)·장면을 못 찾은 [발표 덱에서 보기](`deckLinks`)·가로 넘침(`overflowX`)을 봅니다(`.claude/skills/portfolio-build/SKILL.md` §7-3).
> 고칠 곳은 `src/`의 기술 문서이고(원칙 4 "고칠 곳은 소스다"), 원문이 바뀌었으면 `/portfolio-build`를 다시 실행합니다. `data/`를 손으로 고치지 않습니다.

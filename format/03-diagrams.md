# 기준 ③ Mermaid 다이어그램 5종

> 원본: 「유니티 개발자 취업·기술 문서 작성 가이드 v2」 **Part 4 Mermaid 다이어그램** · **Part 3 ④ 다이어그램 중심** · **Part 6 §6-3**
> (https://koohoo-dev.github.io/portfolio-guide/guide.html#4)
> 이 파일은 Claude가 다이어그램이 **적절한지 점검**하고, 빠진 다이어그램을 **제안**할 때 씁니다.

## 무엇을 설명하느냐에 따라 고르기

| 다이어그램 | 답하는 질문 | 기술 문서 섹션 | Mermaid |
|---|---|---|---|
| **클래스** | 무엇으로 이루어져 있는가? (런타임 구조) | 2. 시스템 구조 | `classDiagram` |
| **시퀀스** | 시간 순서로 어떻게 상호작용하는가? | 2·3. 구조/기능 | `sequenceDiagram` |
| **상태(FSM)** | 어떤 상태를 오가는가? | 2·3. 구조/기능 | `stateDiagram-v2` |
| **플로우차트** | 어떤 갈림길을 지나는가? (로직) | 3. 핵심 기능 | `flowchart` |
| **ER** | 데이터가 어떻게 저장되는가? (저장 구조) | 2. 시스템 구조 | `erDiagram` |

- 하나의 기능에 5개를 다 넣을 필요는 없습니다. **설명하려는 것**에 맞는 1~2개면 충분합니다.
- 흔한 조합: **클래스로 구조** + **플로우차트로 핵심 로직**.
- **클래스 vs ER**: 클래스는 *메모리 위 객체 관계*, ER은 *디스크/DB 위 데이터 관계*.
  세이브·서버 데이터가 있는 프로젝트라면 둘 다 보이면 "런타임과 저장을 모두 이해한다"는 인상을 줍니다.

## 점검 포인트

- [ ] **시스템 구조 섹션**에 다이어그램이 최소 1개 있다 (필수)
- [ ] 다이어그램이 **요약**이다 — 핵심 구성요소만 (클래스 10개 이하 권장)
- [ ] 다이어그램 앞뒤에 **"이 그림에서 봐야 할 것"** 한 줄 설명이 있다
- [ ] 상태 전이가 핵심인 기능(AI·보스·UI 흐름)에 상태 전이 그림이 있다 (권장)
      — `flowchart`로 상태를 그렸어도 전이가 보이면 통과. `stateDiagram-v2`가 더 맞으면 **참고**로 제안
      (판정은 다이어그램 종류가 아니라 **무엇을 보여주는가**로)
- [ ] Mermaid 문법 오류가 없다 (상세 문서에서 렌더 실패 시 빨간 오류 박스가 뜸. 발표 덱은 같은 원문 블록을 그리므로 거기서도 깨짐)
- [ ] 발표 덱 장면에 들어갈 다이어그램이 **노드 10개 안팎 · 가로(`LR`) 방향**이다 — 아래 「발표 덱에서 작아지는 문제」 (참고)

## 발표 덱에서 작아지는 문제

발표 덱은 다이어그램을 1280×720 장면에 **통째로 맞춰** 그립니다. 세로로 길거나 노드가 많으면 그림 전체가 줄어들어
글자가 작아지고, 화면·PDF에서 읽히지 않습니다. 렌더러는 **실효 글자 크기**(글자 크기 × 표시 폭 ÷ 그림 원래 폭)가
**10px 미만**이면 참고 지표 `tiny-diagram`을 남깁니다(빨간 배지 아님, `PFScene.report().info.notes`).

| 증상 | 방향 (리포트에 적는 말) |
|---|---|
| 세로로 긴 `flowchart TD` | `flowchart LR`로 바꾸면 16:9 화면에 맞습니다 |
| 노드가 15개 넘는 클래스 그림 | 핵심 클래스 10개 안팎만 남기고, 나머지는 다른 그림으로 나누세요 |
| 참여자가 많고 긴 시퀀스 | "요청 → 검증"과 "판정 → 결과"처럼 **둘로 나누세요** |
| 노드 글자가 긴 문장 | 라벨은 짧게, 설명은 그림 바깥 한 줄 캡션으로 |

- 리포트 문구 예: "[참고] 발표 덱 7장(§3.2)의 다이어그램이 작아 보입니다(약 8px). 둘로 나누거나 가로(LR)로 바꿔 보세요."
- 고치는 곳은 `src/`의 기술 문서입니다. 발표 덱은 원문 블록을 그대로 그리므로 원문을 고치면 상세 문서·발표 덱이 함께 바뀝니다.

## 빠진 다이어그램을 제안할 때 (프롬프트 틀)

리포트에는 **Mermaid 코드를 대신 써 넣지 말고**, 학생이 직접 AI에게 요청할 수 있는 프롬프트를 제안합니다.
학생이 코드를 받은 뒤 **읽고 고쳐서** 자기 문서에 넣는 것이 원칙입니다.

```text
다음 [무엇]을 Mermaid [다이어그램 종류]로 그려줘.
[구성요소·관계·순서를 목록으로 구체적으로 나열]
[특별히 강조할 표현 방식: 점선/마름모/PK·FK 등]
Mermaid 코드 블록으로만 답하고 설명은 빼줘.
```

## 렌더링 메모

- 상세 문서·발표 덱 모두 Mermaid를 **라이브 렌더**합니다 (이미지 변환 불필요). 발표 덱은 원문 블록을 가리켜 그대로 그립니다(옮겨 적지 않음). GitHub 저장소 뷰에서도 렌더됩니다.
- `%%{init: {'theme':'neutral'}}%%` 같은 init 지시문은 그대로 존중합니다. 없으면 `default` 테마.

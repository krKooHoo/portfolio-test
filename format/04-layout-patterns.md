| 주인공 | 다이어그램·화면·표·코드. 글은 제목 + 도입 1~2줄 + 짧은 조각 | 이름·기술 스택·프로젝트별 대표 화면과 기능 | 기술 문서 md **전문** 그대로 |

## 발표 덱 장면 틀 (`project.html?p=<폴더 이름>`)

렌더러가 고정으로 만드는 장면과, `/portfolio-build`가 `deck.slides[].layout`으로 고르는 장면 틀입니다. 장면 id는 공유 주소(`#s=<id>`)가 됩니다.

| 장면 틀 | 장면 id | Part 3 유형 | 기술 문서 섹션 | 무엇을 | 데이터 |
|---|---|---|---|---|---|
| 표지 (고정) | `cover` | ① 표지 | 문서 시작 | 프로젝트 소개 틀 — 제목·한 줄 소개·큰 대표 이미지·메타 격자·개발 의도·링크 카드(상세 문서 포함)·태그 | `title`, `tagline`, `cover`, `meta`, `intent`, `links`, `tags` |
| 목차 (고정) | `toc` | ② 목차 | 표지 다음 | 장 목록(장면 수·쪽 번호) + 회고 · 더 보기 | `deck.chapters[]` |
| 장 표지 (고정) | `ch-<장 key>` | ② 목차 | 각 H2 | 장 번호·장 이름 + 그 장의 장면 목록 | `deck.chapters[]`, 그 장의 `slides[]` |
| 개요 `overview` | `d-<key>` | ③ 개요 | 1. 개요 | 글 + 메타·그림 | `lead`, `points`, `visuals` |
| 그림 + 번호 카드 `visual` | `d-<key>` | ④ 다이어그램 중심 · ⑦ 흐름 | 2·3. 구조/기능 | 다이어그램·이미지 한쪽 + 번호 카드(`points`) 다른 쪽 | `visuals(kind: mermaid·image)`, `points` |
| 코드 + 설명 `code` | `d-<key>`(나뉘면 `-2`…) | ⑤ 코드+설명 2단 | 3. 핵심 기능 | 코드 **20줄 안팎** + 왜(`points`). 넘으면 "계속" 장면, 참고 `long-code` | `visuals(kind: code, lines)` |
| 큰 그림·표 한 장 가득 `full` | `d-<key>` | ④ · ⑥ 비교 | 2. 구조 · 4. 고민과 선택 | 큰 다이어그램, 비교 표, As-Is/To-Be 표 | `visuals(kind: mermaid·table·image)` |
| 화면 모음 `screens` | `d-<key>` | (Part 1 §3.2 스크린샷) | 3. 핵심 기능 | 스크린샷·GIF 2~3열 + 캡션 | `visuals(kind: image)` 2~3개 |
| 문제 해결 `problem` | `d-<key>` | (Part 1 §3.2 이슈 해결) | 5. 결과 (트러블슈팅) | 문제 → 원인 → 해결 → 결과 + 근거 그림 | `points`, `visuals` |
| 회고 (고정) | `retro`(나뉘면 `retro-2`) | ⑧ 회고 | 5. 결과 및 배운 점 | 달성 · 아쉬움 · 계획 | `retro` |
| 맺음 (고정) | `end` | ⑧ 회고 | 문서 끝 | 마무리 + 상세 문서 링크 | `links` |

- 예전 공유 주소(`#s=hl-n`, `ts-n`, `shots`, `more` 등)는 가까운 새 장면으로 넘어갑니다. 다시 빌드해도 같은 절의 장면은 예전 `key`(주소)를 그대로 쓰고, 절이 바뀐 장면만 주소가 바뀔 수 있습니다(`schema.md` 「key 규칙」).
- 장면이 가리키는 원문 블록을 못 찾으면(0곳) `visual-missing`, 여러 곳이면 `visual-ambiguous`, 원문이 바뀌었으면 `visual-changed` 빨간 띠가 장면 안에 보입니다(배포·PDF에도). 고칠 곳은 원문 또는 다시 빌드.

## 포트폴리오 문서 절 (`index.html`)

위에서 아래로 읽는 한 페이지입니다. 절 id는 공유 주소(`#<id>`)가 되고, 예전 포트폴리오 덱 주소(`#s=<장면 id>`·`#<번호>`)는 같은 절로 넘어갑니다.
머리 막대에 절 이동과 **[PDF로 저장]**(아래쪽 그림까지 받은 뒤 인쇄)이 있습니다.

| 절 | 절 id | 무엇을 | 인쇄(A4) | 데이터 |
|---|---|---|---|---|
| 머리 | `cover` | 이름·영문 이름·한 줄 정체성·연락처 버튼 | 1쪽 위, 버튼 대신 칠 수 있는 주소 | `profile` |
| 자기소개 | `intro` | 자기소개 글(줄바꿈 그대로) | 1쪽 | `profile` |
| 기술 스택 | `stack` | 기술마다 "무엇을 만들며 썼는지" + 근거 프로젝트(같은 페이지의 그 프로젝트로) (패턴 10) | 1쪽 | `skills[]` |
| 프로젝트 소개 | `p-<폴더>` | 대표 이미지 + 장르·기간·인원·환경·내 역할 + 개발 의도 + 태그 + 링크(발표 덱·상세 기술문서·GitHub·영상) | 프로젝트마다 새 쪽, 링크는 주소로 | `cover`, `meta`, `team.role`, `intent`, `tags`, `links` |
| 기능 소개 | `p-<폴더>-core` | 화면은 왼쪽(기능 번호와 함께) · FEATURE 번호 + 제목 + 설명과 [발표 덱에서 보기]는 오른쪽 목록 (패턴 9·11). 화면이 없으면 목록이 폭 전체 | 새 쪽 | `highlights[]`(`image`는 그 기능 절의 이미지만, `section` → 발표 덱 장면) |
| 한눈에 보기 | `glance` | 프로젝트 요약 행(이름·한 줄 소개·핵심 기술·역할·링크) (패턴 11) | 마지막 쪽 | `projects` |
| 연락처 | `contact` | 내 연락처 + 프로젝트별 링크(그 밖의 링크는 주소까지) | 마지막 쪽 | `profile`, `links` |

## 레이아웃 원칙 (Part 3 요약)

- **한 화면 = 한 메시지.** 장면·절마다 무엇을 보여주려는지 하나만. 한 주제는 "구조 → 흐름 → 구현" 여러 장면으로 나눕니다("한 장에 한 항목"이 아님).
- **다이어그램이 주인공**일 때는 그림을 크게, 위 짧은 제목 + 아래 한 줄 캡션. 덱에 넣는 다이어그램은 노드 10개 안팎·가로(`LR`) 권장(기준 ③).
- 색은 **배경 / 텍스트 / 강조 3색 안에서** 통일. 강조색은 `profile.md`의 `강조색` 하나.
- 코드는 다크 블록, 나머지는 밝은 문서형. (**미니멀 / 문서형**이 기본값)
- 최종 제출은 **PDF** — 제출 기본은 **포트폴리오 문서 PDF**(머리 막대의 **[PDF로 저장]**, A4). 발표 덱은 덱 아래 띠의 [PDF로 저장]으로 프로젝트별 16:9 PDF, 상세 문서는 Ctrl+P로 A4(기준 ⑥).

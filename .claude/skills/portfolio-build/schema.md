# 데이터 스키마 (data/)

고정 렌더러(`index.html`, `project.html`, `doc.html`)가 읽는 데이터 형식입니다. **이 형식을 정확히 지킵니다.**
값이 없으면 문자열은 `""`, 배열은 `[]`, 객체 필드는 `null` — **추측해서 채우지 않습니다.**

## `data/portfolio.json`

```json
{
  "generatedAt": "2026-10-21",
  "profile": {
    "name": "홍길동",
    "nameEn": "Gildong Hong",
    "headline": "구조를 설명할 줄 아는 유니티 클라이언트 개발자",
    "intro": "profile.md 자기소개를 줄바꿈까지 그대로",
    "email": "you@example.com",
    "github": "https://github.com/your-id",
    "links": [{ "label": "블로그", "url": "https://your-blog.example.com" }]
  },
  "settings": {
    "layout": "project",
    "accent": "#2F6FEB"
  },
  "skills": [
    {
      "name": "Unity",
      "evidence": [
        { "text": "Animator 기반 FSM으로 보스 패턴 5종 설계", "project": "1-action-platformer" }
      ]
    }
  ],
  "projects": ["00-example-crafting", "0-Tidy-Mommy"]
}
```

| 필드 | 규칙 |
|---|---|
| `profile.*` | **`profile.md`에서만.** 자기소개(`intro`)는 고쳐 쓰지 않고 그대로 |
| `settings.layout` | `"project"` 또는 `"stack"` (profile.md `구성 방식`, 없으면 `"project"`) |
| `settings.accent` | `#RRGGBB` 형식. 형식이 틀리면 `"#2F6FEB"` + 리포트에 알림 |
| `skills[]` | 3~8개. 기술마다 `evidence`(근거)가 **1개 이상**. 근거 없는 기술은 넣지 않음 |
| `skills[].name` | 원문에 나온 기술명, 또는 원문의 **구체 항목을 묶는 상위 범주** (싱글톤·Strategy → "디자인 패턴", `csharp` 코드 → "C#") |
| `skills[].evidence[].text` | "무엇을 만들었는지" 한 줄(40자 내외). 기술 문서에 있는 사실만. 상위 범주로 묶었다면 **원문의 구체 용어**를 문장에 넣음 |
| `skills[].evidence[].project` | 근거 프로젝트의 **폴더 이름** |
| `projects` | 표시 순서대로 폴더 이름 배열. profile.md `프로젝트 순서`가 있으면 그 순서 |

## `data/projects/<폴더 이름>.json`

```json
{
  "id": "1-action-platformer",
  "doc": "기술문서.md",
  "title": "Switch Strike",
  "tagline": "교대 한 번으로 위기를 반격 기회로 바꾸는 2D 사이드뷰 액션 플랫포머",
  "cover": "images/cover.png",
  "team": { "type": "solo", "size": "1인", "role": "" },
  "meta": [
    { "label": "장르", "value": "2D 사이드뷰 액션 플랫포머" },
    { "label": "기간", "value": "2주 (2026.06.24 ~ 2026.07.07)" },
    { "label": "인원", "value": "1인 개발" },
    { "label": "환경", "value": "Unity 6.3, C#, Rider" }
  ],
  "tags": ["Unity 6", "C#", "Kinematic 이동", "Animator FSM"],
  "links": {
    "github": "https://github.com/...",
    "video": "https://www.youtube.com/watch?v=...",
    "extra": [{ "label": "Notion", "url": "https://..." }]
  },
  "highlights": [
    {
      "title": "Kinematic 이동 컨트롤러",
      "what": "기능 설명 — 무엇을 하는가",
      "how": "구현 방법 — 구조·흐름·로직 순으로 한두 문장",
      "why": "선택 이유 — 대안과 비교한 근거",
      "section": "3. 이동 컨트롤러"
    }
  ],
  "troubleshooting": [
    {
      "title": "점프 이동 중 타일 모서리에 끼는 문제",
      "problem": "이슈 상황",
      "cause": "원인 분석",
      "solution": "해결 방법",
      "result": "결과",
      "lesson": "배운 점·회고 (원문에 있을 때만)",
      "section": "3.8 트러블슈팅: 점프 이동 중 타일 모서리에 끼는 문제"
    }
  ],
  "screenshots": [
    { "src": "images/boss_intro.gif", "caption": "보스방 진입 연출" }
  ],
  "retro": {
    "achieved": ["달성한 것 — 측정값이 있으면 그대로"],
    "regrets": ["아쉬운 점(기술 부채)"],
    "plans": ["개선 계획"]
  }
}
```

| 필드 | 규칙 |
|---|---|
| `id` | **폴더 이름 그대로** (파일 이름과 같아야 함) |
| `doc` | 프로젝트 폴더 안 기술 문서 파일 이름 |
| `title` | 문서 제목에서 "기술 문서" 같은 꼬리를 뗀 프로젝트명 |
| `tagline` | 한 줄 소개 = 제목 바로 아래 인용문·부제, 또는 "한 줄 소개" 항목. 있으면 **그대로**. 없으면 What을 40자 내외로 압축 + "확인해 주세요" |
| `cover` | 대표 이미지. 문서가 "대표 이미지"로 지정한 것 → 없으면 첫 이미지 → 없으면 `null` |
| `team.type` | `"solo"` 또는 `"team"` |
| `team.size` | "1인", "3인"처럼 짧게. 중도 이탈 같은 사정은 `meta`의 인원에 |
| `team.role` | **팀: 필수.** 문서의 "내 역할/담당"을 그대로 (여러 곳이면 개요 표 우선). 없으면 `""` + 리포트 **필수**. **개인:** 담당 범위가 적혀 있을 때만, 없으면 `""` + 리포트 **참고**. "1인 개발"에서 "전체"를 유추하지 않음 |
| `meta` | 장르·기간·인원·환경 순(있는 것만). 문서의 개요 표에서 가져옴 (표가 여러 개면 맨 앞 개요 표 우선, 합쳤다면 "확인해 주세요"). 버전은 원문 그대로 |
| `tags` | 4~7개, **15자 내외의 짧은 키워드**. 개발 환경·주요 기술·본문에 실제로 나온 기술·패턴. 버전은 줄여도 됨(`Unity 6000.3.15f1` → `Unity 6.3`). IDE는 제외 |
| `links.*` | 문서·profile에 있는 URL만. `#`·빈 링크는 `""` + 리포트 **권장**. 저장소가 여럿이면 주 저장소를 `github`, 나머지는 `extra`(예: `서버 GitHub`). 기획서·전체 플레이 영상 등도 `extra` |
| `schemaVersion` | `2`. 이 값과 `deck`이 있으면 발표 덱은 `deck`대로 그리고, 없으면(예전 데이터) 핵심 구현·이슈 해결로 **자동 구성**합니다(아래 「발표 덱」) |
| `intent` | 포트폴리오 덱 프로젝트 소개의 "개발 의도". `{ "text", "verbatim" }`(아래 「글 조각」). 문서의 Why(왜, 무엇에 집중했나) 문단에서. 없으면 `null` |
| `highlights` | **2~4개**(포트폴리오 덱의 기능 3열·한눈에 보기용). 핵심 시스템·기능, 또는 구조 섹션의 중요한 설계 결정. `why`는 같은 기능의 "고민과 선택" → 없으면 코드의 `(Why)` 주석·본문 설명 → 그래도 없으면 `""` + 리포트 **필수**. `how`와 `why`는 **같은 결정**을 말해야 함. `image`(선택): 그 기능 절(`section`)에 실제로 있는 이미지 하나 `{ "src", "w", "h", "caption" }` — 없으면 `null` |
| `troubleshooting` | **0~3개.** 트러블슈팅 섹션 우선, 없으면 본문의 문제→해결 서술. `result`는 **해결 뒤 달라진 점**만 — 없으면 `""` + 리포트 권장(배운 점을 `result`로 옮기지 않음). 배운 점·회고는 `lesson`. 한 절에 사례가 2개면 하나로 묶어도 됨 |
| `screenshots` | (포트폴리오 덱·자동 구성용) **최대 6장**, 이미지 파일(`.png .jpg .jpeg .gif .webp`)만. 6장보다 많으면 `highlights` 기능의 화면 우선 + 기능이 겹치지 않게. `caption`은 alt → 짧으면 주변 제목·표 머리와 조합(조합했으면 "확인해 주세요") |
| `retro` | 문서의 결과·회고 섹션에서. 각 배열 1~4개. 4개보다 많으면 개요의 Why와 관련이 큰 순. `regrets[i]`와 `plans[i]`는 같은 항목끼리 짝. `section`: 회고 절 제목 그대로(없으면 `""`) |
| `w`, `h` | (선택) `screenshots[]`·`highlights[].image`·발표 덱 이미지의 픽셀 크기. 이미지 파일 머리에서 읽은 값만(추측 금지). 없으면 렌더러가 실행 중에 잽니다 |
| `section` | 원문 **제목 텍스트 그대로**(앞의 `#` 제외, 코드 블록 안의 `#` 줄은 제목 아님). `how`가 설명된 **가장 구체적인 하위 절** 우선. 렌더러가 이 텍스트로 원문 위치 링크를 만듦 (`★`·`①`·`:` 등 특수문자 그대로 두어도 됨) |

### "그대로"와 "압축"의 구분

- **그대로**: 굵게·기호 제거, 주어·어미 정리 정도만 한 경우. "확인해 주세요"에 넣지 않음.
- **압축**: 여러 문장을 합치거나, 표현을 바꾸거나, 여러 섹션을 조합한 경우. 반드시 "확인해 주세요"에 넣음.

### 경로 규칙

- `cover`, `screenshots[].src`는 **프로젝트 폴더 기준 상대경로** (`images/...`). 문서에 적힌 경로 그대로.
- 실제 파일 이름과 **대소문자까지 일치**해야 합니다 (GitHub Pages는 대소문자를 구분).
- 텍스트 필드에는 마크다운을 쓰지 않습니다. 단, 코드명은 `` `백틱` ``을 써도 됩니다 (렌더러가 코드 스타일로 표시).

## 발표 덱 `deck` (`schemaVersion: 2`)

`project.html?p=<폴더>`(발표 덱)이 그리는 장면 목록입니다. 기술 문서를 바탕으로 한 16:9 발표 슬라이드이고,
**그림·코드·표·이미지는 원문 블록을 가리키기만** 합니다. 렌더러가 원문 md에서 그 블록을 찾아 **그대로** 그립니다(옮겨 적지 않음).
장면에 들어가는 글은 짧은 글 조각(`lead`, `points`)뿐입니다.

```json
"deck": {
  "chapters": [
    { "key": "spawn", "title": "시스템 ② 스폰·난이도 곡선", "sectionPath": ["4. 시스템 ② 스폰·난이도 곡선 ★"] }
  ],
  "slides": [
    {
      "key": "spawn-weight",
      "chapter": "spawn",
      "layout": "visual",
      "tab": "구현",
      "title": { "text": "4.3 핵심 기능 ①: 레벨별 지수 가중치", "verbatim": true },
      "lead": { "text": "레벨마다 지수를 바꿔 같은 식으로 도와주는 스폰과 방해하는 스폰을 만듭니다.", "verbatim": false },
      "sectionPath": ["4. 시스템 ② 스폰·난이도 곡선 ★", "4.3 핵심 기능 ①: 레벨별 지수 가중치"],
      "points": [
        { "label": "구현", "text": "색별 가중치 = (화면의 그 색 개수 + 1) ^ 지수", "verbatim": false }
      ],
      "visuals": [
        { "kind": "image", "src": "images/spawn_weight_by_level.png", "w": 1200, "h": 700, "caption": { "text": "레벨별 다음 블록 색 확률", "verbatim": true } },
        { "kind": "code", "n": 1, "lines": [1, 18], "fp": "private BlockColor PickColor(int level)" }
      ]
    }
  ]
}
```

### 장(`chapters[]`)

- 원문 `##`(H2) 순서 그대로. **목차 H2**(`목차`·`차례`·`Contents`)는 빼고, 개요 앞의 요약 H2(예: `0. 한 장 요약`)는 장으로 만들지 않고 표지·개요 재료로만 씁니다.
- `title`은 원문 제목에서 번호·`★` 같은 기호만 뗀 글자(그대로 취급). `sectionPath`는 그 H2 제목 그대로 한 칸.
- `key`: 아래 「key 규칙」.

### 장면(`slides[]`)

| 필드 | 규칙 |
|---|---|
| `key` | 장면 주소(`#s=d-<key>`)가 됩니다. 「key 규칙」 |
| `chapter` | 속한 장의 `key` |
| `layout` | 장면 틀. `"overview"` 개요(글 + 메타·그림) · `"visual"` 그림 + 번호 카드 · `"code"` 코드 + 설명 · `"full"` 큰 그림·표 한 장 가득(비교 표·As-Is/To-Be 표도 여기) · `"screens"` 화면 2~3열 · `"problem"` 문제 해결(문제 → 원인 → 해결 → 결과 + 근거 그림) 중 하나. 표지·목차·장 표지·회고·맺음 장면은 렌더러가 만듭니다 |
| `tab` | 장면 머리 오른쪽 작은 라벨. `"개요"` `"구조"` `"흐름"` `"구현"` `"선택"` `"문제 해결"` `"결과"` 중 하나, 또는 `""` |
| `title` | 글 조각. 기본은 `sectionPath` 마지막 제목 그대로(`verbatim: true`). 짧게 줄였으면 `verbatim: false` |
| `lead` | 글 조각 하나(도입 1~2문장, 80자 안팎) 또는 `null` |
| `sectionPath` | 이 장면이 다루는 원문 절. 「절 경로」 |
| `points` | 글 조각 0~4개. `label`은 원문의 굵은 머리말·표 머리·`기능`·`구현`·`이유`·`문제`·`원인`·`해결`·`결과`·`배운 점` 같은 짧은 라벨 또는 `""` |
| `visuals` | 0~3개. 「원문 블록 참조」. `layout`이 `visual`·`code`·`full`이면 1개 이상, `screens`는 이미지 2~3개 |

### 글 조각 `{ "text", "verbatim" }`

- `verbatim: true`는 **원문 그 절 범위 안에 같은 글자가 그대로 있을 때만**(굵게·기울임·백틱 기호와 공백 차이는 무시). 빌드가 이것을 검사합니다.
- 그 밖에 줄이거나 합치거나 바꾼 글은 모두 `verbatim: false` → 리포트 **"확인해 주세요"**에 장면별로 넣습니다.
- 글자 수: `title` 40자, `lead` 80자, `points[].text` 90자 안팎. 넘치면 렌더러가 줄이고 그래도 넘치면 장면을 나눕니다.

### 절 경로 `sectionPath`

- 원문 제목 글자 그대로의 배열, **위에서 아래로**(예: `["4. 시스템 ②…", "4.3 핵심 기능 ①…"]`). 마지막 칸이 그 절입니다.
- 같은 제목이 문서에 여러 번 나오면(예: `#### 개요`가 7곳) **구분될 때까지 위 제목을 앞에 붙입니다.** 렌더러는 마지막 칸과 일치하는 제목 중 앞 칸 제목들을 순서대로 조상으로 가진 것을 찾고, **정확히 1곳일 때만** 씁니다. 0곳·2곳 이상이면 그 자리에 빨간 띠("원문에서 찾지 못했습니다" / "원문 위치가 여러 곳입니다")를 그립니다.

### 원문 블록 참조 `visuals[]`

| kind | 찾는 법 |
|---|---|
| `"mermaid"` | 그 절 범위의 `mermaid` 코드 블록 중 `n`번째(1부터) |
| `"code"` | 그 절 범위의 **mermaid가 아닌** 코드 블록 중 `n`번째. 언어 표시가 없는 블록도 셉니다(평문으로 그림). `lines: [시작, 끝]`(선택, 블록 안 줄 번호, 펜스 줄 제외, 1부터) — 20줄을 넘으면 렌더러가 "계속" 장면으로 나눕니다 |
| `"table"` | 그 절 범위의 표 중 `n`번째. 표 안의 이미지는 표째로만 참조합니다 |
| `"image"` | `src`(기술 문서에 적힌 경로 그대로)로 찾습니다. 표 밖 이미지만. 같은 `src`가 그 절에 두 번 나오면 `n` 필수 |

- **그 절 범위** = `sectionPath` 마지막 제목부터 **다음 제목(수준과 관계없이) 바로 앞까지**. 하위 절의 블록은 하위 절 경로로 가리킵니다. 참조마다 `sectionPath`를 따로 줄 수 있고, 없으면 장면의 `sectionPath`를 씁니다.
- `fp`(지문, `code`·`mermaid`·`table`에 필수): `code`·`mermaid`는 블록의 첫 번째 비어 있지 않은 줄(앞뒤 공백 제거, 60자까지. `mermaid`는 `%%`로 시작하는 지시 줄을 건너뜀), `table`은 머리 칸 글자를 `|`로 이은 것. 원문이 바뀌어 지문이 다르면 렌더러가 띠("원문이 바뀌었습니다 → /portfolio-build 다시")를 그립니다.
- `caption`: 이미지는 원문 alt가 기본(`verbatim: true`). 다른 블록은 없어도 됩니다.
- 이미지의 `w`·`h`는 파일 머리에서 읽은 값만.

### key 규칙

- 영문 소문자·숫자·하이픈만, 2~32자, 영문 소문자로 시작(`^[a-z][a-z0-9-]{1,31}$`). `s-숫자`·숫자만은 금지.
- 다시 빌드할 때 **같은 `sectionPath`의 장·장면은 예전 `key`를 그대로** 씁니다(공유한 `#s=` 주소가 유지되게). 예전 data가 없으면 절 내용을 나타내는 짧은 영어 낱말로 만듭니다(예: `spawn-weight`). 덱 안에서 겹치면 안 됩니다.
  - 한 절에 장면이 여럿이면(구조·흐름·구현으로 나눈 경우) 예전 장면 중 **시각 자료(kind·n·fp 또는 src)가 가장 많이 겹치는** 장면의 key를 이어 받습니다. 겹치는 예전 장면이 없으면 새 key.
  - 예전 data에 `deck.base`가 있으면 그것이 **빌드가 만든 예전 장면 목록**입니다(`deck.slides`는 장면 고치기가 반영된 것). key를 이어 받을 때는 `deck.base`를 보고, `edited: true` 장면은 옮겨 적지 않습니다.
  - 장면 고치기 파일(아래)의 `pin[].key`와 `hide`의 key는 **다른 절의 장면에 쓰지 않습니다.**
- 렌더러는 장면 id를 `d-<key>`(코드가 나뉘면 `d-<key>-2`…, 표가 하한에서도 안 들어가 행을 나누면 `d-<key>-t1`…)로 씁니다. 규칙에 맞지 않는 key는 렌더러가 순번 id로 바꾸고 감사에 남깁니다.

### 분량

- 프로젝트당 장면 **15~30장 권장**(렌더러가 만드는 표지·목차·장 표지·회고·맺음 포함). 30장을 넘으면 리포트 **참고**. 15장보다 적은 것은 지적하지 않습니다(짧은 문서).
- 30장을 넘기면 같은 절의 두 번째 코드 → 보조 표 → 겹치는 화면 순으로 빼고, 빠진 내용은 상세 문서에 있으니 그대로 둡니다.

### 예전 데이터(자동 구성)

`schemaVersion`이 없거나 `deck`이 없으면 렌더러가 `highlights`·`troubleshooting`·`screenshots`·`retro`로 덱을 만들고, 각 항목의 `section`이 **정확히 1곳**으로 풀릴 때만 그 절의 첫 그림(이미지·mermaid·코드 순)을 붙입니다.
장면마다 작은 띠("예전 데이터로 자동 구성 — /portfolio-build를 다시 실행하면 발표 덱이 됩니다")가 보입니다.

## 장면 고치기 파일 `src/<폴더>/deck-edits.json`

발표 덱 장면을 수강생 요청으로 고친 결과입니다(`/portfolio-edit`가 씀). **수강생 소유 소스**라 커밋하고, `/portfolio-build`는 읽기만 하고 쓰지 않습니다.
기술 문서가 아니므로(`.md` 아님) 빌드·점검이 문서로 읽지 않습니다. 다시 빌드해도 고친 내용이 남는 이유는 이 파일이 `data/`가 아니라 `src/`에 있기 때문입니다.

```json
{
  "schemaVersion": 1,
  "pin": [
    { "key": "spawn-weight", "chapter": "spawn", "layout": "full", "tab": "구현",
      "title": { "text": "4.3 핵심 기능 ①: 레벨별 지수 가중치", "verbatim": true }, "lead": null,
      "sectionPath": ["4. 시스템 ② 스폰·난이도 곡선 ★", "4.3 핵심 기능 ①: 레벨별 지수 가중치"],
      "points": [], "visuals": [{ "kind": "table", "n": 1, "fp": "레벨|지수" }],
      "from": { "key": "spawn-weight", "sectionPath": ["…"], "sig": ["…"] } },
    { "key": "spawn-weight-code", "after": "spawn-weight", "chapter": "spawn", "layout": "code", "…": "…" }
  ],
  "hide": [{ "key": "spawn-chart", "from": { "…": "…" } }],
  "portfolio": null
}
```

| 필드 | 규칙 |
|---|---|
| `pin[]` | **장면 통째**(위 「장면」 규칙 그대로: `key`·`chapter`·`layout`·`tab`·`title`·`lead`·`sectionPath`·`points`·`visuals`) + 선택 `after`·`from`. 배열 순서 = 적용 순서. 빌드 장면과 key가 같으면 그 장면을 바꾸고, 없으면 새 장면 |
| `pin[].after` | 같은 장 안에서 이 장면 바로 뒤에 놓을 장면 key. 없거나 숨긴 장면이면 옮기지 않음(새 장면은 그 장 끝) |
| `pin[].from`·`hide[].from` | 닻: 원래 빌드 장면의 `key`·`sectionPath`·시각 자료 서명. `deck-edits.py pin`·`hide`가 채우며 **손대지 않습니다**. 다시 빌드로 key가 바뀌어도 같은 절(제목 그대로)·같은 그림의 장면을 찾아 다시 붙이는 데 씀. 절 제목이 바뀌면 다시 붙지 않습니다(고아) |
| `pin[].group`·`hide[].group` | 묶음: 나누기(`pin --as`)·합치기(`hide --into`)로 함께 생긴 항목. `undo`는 같은 묶음을 함께 지움. 스크립트가 채우며 손대지 않습니다 |
| `hide[]` | 숨길 장면. `{ "key", "from" }` 또는 key 글자 |
| `portfolio` | 포트폴리오 덱 고치기 자리(2차, 지금은 `null`). 식별자는 `highlights[].section` |

- **글 조각**은 둘뿐입니다: `verbatim: true`(그 절 원문 또는 절 경로의 제목에 같은 글자가 있음 — 스크립트가 검사) · `verbatim: false`(Claude가 줄임 → 리포트 "확인해 주세요").
  원문에 없는 새 문장·수치는 넣지 않습니다(수강생이 직접 쓰고 싶은 문장은 기술 문서에 먼저 쓰고 다시 빌드).
- **다른 절의 원문 블록**도 가리킬 수 있습니다(수강생이 요청할 때). 참조마다 자기 `sectionPath`를 적고, "확인해 주세요"에 기록됩니다.
- 장 제목(원문 H2)과 렌더러 장면(표지·목차·장 표지·회고·맺음)은 고치지 않습니다.

**반영**: `python .claude/skills/portfolio-build/deck-edits.py apply <폴더>|--all` (결정적·멱등, Python 3.8 이상·표준 라이브러리만). `data/projects/<폴더>.json`의 `deck`에 다음을 씁니다
(deck 값만 바꿔 끼우므로 나머지 글자는 그대로지만, deck 블록은 스크립트의 줄 모양으로 바뀌고 되돌린 뒤에도 그 모양이 남습니다 — 내용은 같음).
스크립트는 원문 블록 지문(코드·mermaid·표·그림 경로)도 미리 대조해 다르면 `[권장]`으로 알립니다(최종 판정은 미리보기 감사).
명령은 `apply`·`check`·`show`·`pin [--as]`·`add --after`·`hide [--into]`·`undo [--all]`(스크립트 머리말).

| data 필드 | 뜻 |
|---|---|
| `deck.slides` | 고치기를 반영한 장면 목록(렌더러가 그리는 것) |
| `deck.base` | 빌드가 만든 장면 목록(되돌리기용). 고친 것이 없으면 없음 |
| `deck.applied` | 반영 결과 지문. `slides`가 스크립트 결과인지(그러면 `base`가 원본) 빌드가 새로 쓴 것인지(그러면 그것이 새 원본) 가림 |
| `deck.slides[].edited` | `true` = 고친 장면(빨간 띠 문구가 "/portfolio-edit로 고치세요", 미리보기 개요에 ✎) |

`/portfolio-build`는 `base`·`applied`·`edited`를 직접 쓰지 않습니다(스크립트 몫). 스크립트 출력의 `[필수]`·`[권장]`·`[참고]`는 리포트의 같은 등급으로, "확인해 주세요" 줄은 리포트 "확인해 주세요"로 옮깁니다.
고아(다시 빌드로 원래 장면을 잃은 고친 장면)는 반영하지 않고 **권장**으로 알리며, 깨진 원문 참조는 지금처럼 빨간 띠(`visual-*`)로 보입니다.
**숨긴** 장면의 주소(`#s=d-<key>`, `deck.base`에 남아 있음)는 렌더러가 같은 절(절 경로 전체가 같은)의 남은 장면 → 그 장 표지 → 목차 순으로 넘기고,
다시 빌드로 **없어진** 장면·장의 주소는 목차로 넘깁니다. 나뉜 장면 주소 `d-<key>-2`·`d-<key>-t1`이 없으면 `d-<key>`로 갑니다.

# /portfolio-build — 포트폴리오 데이터 생성

대상: `$ARGUMENTS` (비어 있으면 `src/`의 모든 프로젝트, 폴더 이름이면 그 프로젝트만 다시 만듦)

시작 전에 `CLAUDE.md`의 **반드시 지킬 원칙**을 다시 확인합니다. 핵심은 **지어내지 않기**와 **수강생 문서를 고쳐 쓰지 않기**입니다.

## 0. 준비 — 기준 읽기

1. [schema.md](schema.md) — 출력 형식 (반드시 이 형식대로)
2. `format/01-portfolio.md` — 요약·상세 페이지 항목과 체크리스트
3. `format/02-tech-document.md` — 5단 구조 판정 기준
4. `format/03-diagrams.md` — 다이어그램 점검 기준
5. `profile.md`

## 1. 프로젝트 찾기

- `src/*/`에서 `_`로 시작하지 않는 폴더 = 프로젝트. 폴더 이름이 곧 `id`.
- 기술 문서 = 폴더 바로 아래의 `.md` 파일 (`기술문서.md` 우선, 없으면 `README.md`, 그것도 없으면 유일한 `.md`).
  `.md`가 없으면 그 프로젝트는 건너뛰고 리포트에 "기술 문서 없음"으로 적습니다.
- `images/`의 실제 파일 목록, `code/`의 `.cs` 목록을 Glob으로 확보해 둡니다.

## 2. 프로젝트별 추출

각 프로젝트의 기술 문서를 **끝까지** 읽고 [schema.md](schema.md)의 `data/projects/<id>.json`을 채웁니다.
프로젝트가 3개 이상이면 **프로젝트마다 서브에이전트를 병렬로** 띄워도 됩니다
(각 에이전트에 `CLAUDE.md`·schema.md·format/01·02·03 경로와 이 단계·§4의 규칙을 넘김. profile.md는 필요 없음.
에이전트는 `data/projects/<id>.json`을 직접 쓰고 ① 문서 유형 ② 점검 항목 ③ "확인해 주세요" 목록 ④ 기술 스택 근거 후보
(`기술 | 근거 문장 | 원문 섹션`) ⑤ 스크린샷·링크·code/ 통계를 돌려줌. portfolio.json·report.md는 부모가 씀).

추출 규칙:

- **원문에 있는 것만.** 문장은 압축해도 되지만 사실·수치·기술명을 더하지 않습니다.
- 무엇이 "그대로"이고 무엇이 "압축"인지는 [schema.md](schema.md)의 구분을 따릅니다. **압축한 필드**는 목록으로 기억해 두었다가 리포트 "확인해 주세요"에 넣습니다.
- `highlights`: 문서의 **핵심 시스템/기능 섹션**에서 2~4개. `why`는 같은 기능의 "고민과 선택"에서 찾습니다.
  흩어져 있으면(B형 문서) 해당 기능 근처의 선택 근거를 씁니다. 근거가 없으면 `""`.
- `troubleshooting`: 문서의 트러블슈팅에서 임팩트가 큰 순으로 최대 3개.
- `screenshots`: `images/`에 **실제로 있는** 파일 중, 서로 다른 기능을 보여주는 최대 6장. 커버와 겹치지 않게.
- `section`: 원문 제목 텍스트를 **글자 그대로** 복사 (`### ` 같은 기호만 제외).
- 팀 프로젝트면 `team.role`을 반드시 찾습니다. 없으면 `""`로 두고 리포트 **필수** 항목.

## 3. 프로필·기술 스택

- `profile`·`settings`는 `profile.md`에서만. 자기소개는 줄바꿈까지 그대로.
- `profile.md` 값이 예시 그대로(홍길동, you@example.com, your-id)면 그대로 싣되 리포트 **필수**에 "예시 값을 바꾸세요".
- `skills`: profile.md 기술 스택 메모의 기술마다 프로젝트 문서에서 근거를 찾아 `evidence`를 만듭니다.
  메모가 비어 있으면 여러 프로젝트에 공통으로 등장하는 기술 위주로 3~8개 고릅니다.
  **근거를 못 찾은 기술은 빼고** 리포트에 알립니다.
- `projects`: profile.md `프로젝트 순서` → 없으면 폴더 이름 순. 순서에 적힌 이름은 실제 `src/` 폴더 이름과 **대소문자까지** 맞춰 보고,
  맞는 폴더가 없는 이름은 싣지 않고 리포트 **필수**에 적습니다.
- 폴더 이름 하나만 다시 만드는 경우: 그 프로젝트 JSON만 다시 쓰고, `portfolio.json`은 `skills`의 해당 프로젝트 근거와 `projects` 목록만 갱신합니다.

## 4. 검증 (쓰기 전에 반드시)

- [ ] 모든 `cover`·`screenshots[].src`가 Glob 결과와 **대소문자까지 일치**하는 실제 파일이다
- [ ] 모든 `section` 텍스트가 원문에 제목으로 존재한다 (Grep으로 확인 — **코드 블록 밖의** `#` 줄만 제목)
- [ ] 모든 URL이 `http(s)://`로 시작한다 (`#`, `(#)`, 빈 링크는 `""` + 리포트)
- [ ] `tags`의 기술명이 원문에 실제로 등장한다. `skills`는 기술명 또는 그 근거가 된 구체 용어가 등장한다
- [ ] `code/`가 있으면: 문서 코드 블록에 나온 **주요 클래스·메서드 이름**이 `code/`에 존재하는지 표본 확인
      (불일치는 리포트 **권장** — "문서 코드와 실제 코드가 다릅니다")
- [ ] `portfolio.json`의 `projects`마다 같은 이름(대소문자까지)의 `src/<id>/` 폴더와 `data/projects/<id>.json`이 있다
      (Windows는 대소문자를 무시해 미리보기에서는 열리지만, GitHub Pages에서는 그 프로젝트가 덱에서 빠집니다.
      대소문자만 다른 예전 JSON이 남아 있으면 지운 뒤 새로 씁니다 — Windows는 덮어써도 예전 이름을 유지합니다)
- [ ] JSON이 문법적으로 유효하다 (작성 후 다시 읽어 확인. 예: `python -c "import json,sys;json.load(open(sys.argv[1],encoding='utf-8'))" <파일>`
      — Windows에서 한글 출력이 깨지면 `PYTHONIOENCODING=utf-8`)

## 5. 쓰기

- `data/portfolio.json`, `data/projects/<id>.json`을 씁니다. `generatedAt`은 오늘 날짜.
- 더 이상 `src/`에 없는 프로젝트의 `data/projects/*.json`은 지웁니다 (지우기 전에 목록을 사용자에게 알림).

## 6. 점검 리포트 → `report.md`

`format/01`·`02`·`03`의 체크리스트로 판정해 아래 형식으로 씁니다. 같은 기준을 프로젝트마다 똑같이 적용합니다
(예: 자리표시자 링크 `#`는 항상 **권장**, 팀 프로젝트 역할 없음은 항상 **필수**). **문제와 방향만** 쓰고, 고친 문장을 대신 써 주지 않습니다.

```markdown
# 포트폴리오 점검 리포트 (YYYY-MM-DD)

## 요약
| 프로젝트 | 문서 유형 | 필수 | 권장 | 스크린샷 | 링크 |
|---|---|---|---|---|---|
| Switch Strike | B. 다기능 | 0 | 2 | 6/6 | GitHub ✓ · 영상 ✓ |

## 확인해 주세요 (Claude가 요약한 문장)
> 아래는 원문을 압축해 만든 문장입니다. **내 의도와 맞는지 직접 확인**하고, 다르면 원문(src/)을 고친 뒤 다시 빌드하세요.
- [Switch Strike] 기술 스택 근거 "…" ← 원문 §3.1

## 프로젝트별 점검
### Switch Strike (`src/1-action-platformer/기술문서.md`)
- **[필수]** … (기준: format/02 §4 고민과 선택) → 방향: …
- **[권장]** …

## 프로필
- …

## 다음 할 일
1. …
```

빠진 다이어그램을 제안할 때는 `format/03-diagrams.md`의 프롬프트 틀을 채운 **요청 문장**을 제안합니다 (Mermaid 코드를 대신 쓰지 않음).

## 7. 미리보기와 마무리 보고

1. 로컬 서버를 백그라운드로 띄웁니다: `python -m http.server 4600` (실패하면 `py -m http.server 4600`).
   이미 떠 있으면 재사용. 브라우저 도구가 있으면 세 페이지를 열어 콘솔 오류·깨진 이미지가 없는지 확인합니다.
   - `http://localhost:4600/`(포트폴리오 덱)과 프로젝트마다 `project.html?p=<id>`(요약 덱):
     `await PFScene.whenReady()` 뒤 `PFScene.report()`의 `audit`을 읽습니다. `clipped`(빨간 "내용이 잘렸습니다" 띠 —
     배포된 페이지와 PDF에도 나옴)가 있으면 그 장면과 줄여야 할 원문 항목(제목·한 줄 소개·역할·핵심 구현 설명 등)을
     리포트 **권장**에 적습니다. 다른 항목(`head-overlap`·`outside` 등)도 같은 방식으로 적습니다.
   - 프로젝트마다 `doc.html?p=<id>`(상세 기술문서): 기술 문서 안의 이미지는 이 페이지에서만 불러오므로 깨진 이미지는 여기서 확인합니다.
   - 콘솔 경고 `[portfolio] 상세 문서에서 절 제목을 찾지 못함`·`[doc] 요약 덱 대상 제목을 찾지 못함`이 보이면
     `section` 값이 원문 제목과 다른 것입니다. §4의 `section` 검증을 다시 해서 고쳐 씁니다.
2. 사용자에게 짧게 보고합니다:
   - 만든/갱신한 프로젝트 수, 미리보기 주소
   - **필수** 항목 개수와 가장 중요한 3가지
   - "확인해 주세요" 목록을 꼭 읽어 달라는 안내
   - 다음 단계: 소스 수정 → `/portfolio-build` 다시 → 만족하면 commit·push (배포는 `format/06-deploy.md`)

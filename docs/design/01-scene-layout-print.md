## 0. 요약

1. **R-A·R-B는 Windows의 Chrome·Edge에서 구현할 수 있습니다.** 보장 범위도 Windows PC의 Chrome·Edge뿐입니다. macOS는 확인하지 않고 보장하지 않습니다(【R0 결정】 Q1-b, §1-4). 근거와 그 종류는 다음과 같습니다[print-engine §0, paginator §3-5].
   - **프로토타입 실측**: CDP(Chrome DevTools Protocol, 프로그램으로 브라우저를 조종하는 통로)로 만든 PDF 61개 이상(샘플 4편 + 스트레스 문서, 배경 그래픽 켬·끔). 모두 "장면 수 = PDF 쪽 수", 모든 쪽 960×540pt(정확히 16:9), 쪼개진 장면·빈 쪽·넘친 내용 0.
   - **데모 미리보기**: 실제 Ctrl+P 대화상자에서 데모 7장면 페이지의 여백 4종 미리보기가 모두 7쪽이었습니다. **저장된 PDF 파일 자체는 미확인**이고, 여백 "최소·맞춤"에서는 머리글·바닥글 체크가 나타나므로 보장 범위 밖입니다(§1-4, §8-6).
   - 통합 설계(이 문서) 자체는 아직 시험하지 않았습니다(위 근거 표기).
2. **핵심은 CSS가 아니라 렌더러가 내용을 장면으로 나누는 것입니다.** CSS만으로는 긴 기술 문서를 고정 크기 상자에 흘려 넣을 수 없습니다. 브라우저에게 쪽 나누기를 맡기면 R-B가 금지한 잘림과 빈칸이 그대로 생깁니다[spec-impact §2, E7]. 그래서 **측정한 뒤 나누는 분할기(paginator)** 가 필수입니다.
3. **캔버스는 1280×720 CSS px 하나로 고정합니다.** PDF로는 960×540pt(13.333×7.5in)이며 PowerPoint 와이드 화면과 같은 크기입니다. 본문은 16px(PDF 12pt)입니다(§2).
4. **R-B를 그대로 받아들이면 안 되는 점이 다섯 가지 있습니다**(§1-3).
   - 16:9 쪽은 "PDF로 저장"에서만 성립합니다.
   - CDP 결과와 실제 대화상자 결과가 다릅니다.
   - 장면 안의 여백은 사라지지 않습니다.
   - 세로로 긴 다이어그램은 읽기 어려워집니다.
   - 휴대폰 세로 화면에서는 16:9 장면의 글자가 너무 작습니다(본문 약 4.5px).

   R0에서 **R-B의 운영 정의**(Q1, 추천안 4조건 그대로, §1-4)와 **좁은 화면 방식**(Q2)을 정했습니다. 【R0 결정】 Q2는 추천(휴대폰은 문서 보기)과 달리 **모든 화면에서 장면을 그대로 축소**합니다. 화면 = PDF가 어디서나 같아지는 대신, 휴대폰에서는 손가락 확대(pinch zoom)로 읽어야 하고 WCAG 1.4.10(리플로)을 충족하지 못합니다. 이것은 수용한 리스크입니다(§7-6, §12).
5. **화면 보기는 하나뿐입니다: 장면을 통째로 맞춤 축소합니다**(§7-2). 배율 k = min(vw / 1280, vh / 720)이고 남는 곳은 레터박스입니다. 배율 방식은 `transform: scale(k)`가 기본입니다(§7-1). 분할은 인쇄와 같은 k=1에서 하고, 화면은 그 결과를 그대로 확대·축소만 하므로 "화면 = PDF"가 구조적으로 보장됩니다. 글자가 더 선명한 `zoom`은 k≥1.1에서만 쓰는 혼합 방식을 R0에서 검증한 뒤 채택 여부를 정합니다.
6. **고정 렌더러와 `/portfolio-custom`은 공용 장면 키트 하나를 씁니다**(§9). 키트 없이 만든 custom 페이지는 Letter 세로 7쪽으로 나왔고 장면이 쪼개졌습니다. 키트를 싣고 규칙을 지키면 4/4쪽이었습니다(**zoom 기반 프로토타입 키트**와 별도 준비 신호로 잰 값)[screen-ux §7]. custom은 데이터를 실행 중에 받으므로, 반복 데이터는 측정 기반 분할(`PFScene.flow`)로만 그리게 합니다(§9-5).
7. **장면 수가 늘어납니다.** 샘플 상세 페이지는 프로젝트 하나에 약 16~79장면입니다(추정, §5-5). 【R0 결정】 Q3: 요약 합본(`deck.html`)은 만들지 않습니다. 학생은 `project.html`을 프로젝트마다 따로 저장하고, 쪽 수가 부담되면 HUD "요약만"(샘플 기준 프로젝트당 4~7쪽)을 고릅니다. 랜딩 `index.html`도 장면 페이지라 따로 저장할 수 있습니다(5쪽). 대가는 제출 PDF가 "프로젝트 수 + 1"개 파일로 나뉜다는 점입니다(§5-3).

## 1. 요구 해석과 이의 제기

### 1-1. R-A 해석

| 요구 문구 | 이 설계의 해석 | 근거 |
|---|---|---|
| "모든 페이지" | **포트폴리오 페이지만**: `index.html`(랜딩), `project.html`(상세 + 기술 문서 전문), `custom/index.html`(직접 생성 모드). 요약 합본 `deck.html`은 만들지 않습니다(Q3 결정, §5-3). Pages로 함께 공개되는 도구 페이지(`tools/style-lab/index.html` 등)는 포함하지 않고, 대신 `<meta name="robots" content="noindex">`를 넣습니다 | 요구 원문 |
| "16:9 화면에 최적화" | 내용을 **1280×720 논리 캔버스**에 맞춰 짜고, 화면에서는 캔버스를 통째로 확대·축소합니다. 장면 안 배치는 보는 사람의 창 크기와 무관합니다 | [paginator §0, screen-ux §2] |
| "한 장면씩 연결" | 페이지 = 16:9 장면을 세로로 이어 붙인 덱(deck, 슬라이드 묶음)입니다. 스크롤과 키보드로 장면 단위로 넘깁니다 | [screen-ux §4] |
| (해석 확장) 모든 화면 크기 | 【R0 결정】 Q2: 휴대폰·태블릿 세로·좁은 창을 포함해 **모든 화면에서 장면 보기 하나**만 둡니다. k = min(vw / 1280, vh / 720)로 장면을 통째로 맞춰 축소하고 남는 곳은 레터박스입니다. 그래서 화면 = PDF가 어디서나 같습니다. 휴대폰 세로에서는 본문이 약 4.5px로 보이므로 손가락 확대(pinch zoom)를 막지 않습니다(§7-2, §7-6). 추천안(좁은 화면은 문서 보기, 마우스 데스크톱은 폭 맞춤)은 채택하지 않았습니다 | [screen-ux §3, §5] |

데스크톱에서도 브라우저 창은 정확히 16:9가 아닙니다. FHD 모니터에서 창을 최대화하면 주소창과 작업 표시줄 때문에 뷰포트가 약 2.03:1이 되어 좌우에 빈 띠(레터박스)가 생깁니다. 정확한 16:9 화면은 전체 화면 버튼(Fullscreen API)으로 얻습니다[screen-ux §3].

### 1-2. R-B 해석

| 요구 문구 | 이 설계의 해석 |
|---|---|
| "웹 브라우저의 인쇄 기능" | Windows PC의 Chrome·Edge 인쇄 대화상자에서 대상 **"PDF로 저장"**. 페이지의 [PDF로 저장] 버튼은 준비를 기다린 뒤 같은 대화상자를 엽니다 |
| "한 장의 내용이 깨짐 현상" | 장면 하나가 두 쪽으로 쪼개지지 않고, 장면 안 내용이 상자 밖으로 넘쳐 잘리지 않으며, 그리는 도중의 화면이 인쇄되지 않습니다 |
| "한 페이지를 두 페이지로 나누어 생긴 빈칸" | 쪽 나눔 때문에 생기는 빈 쪽·반쪽짜리 쪽이 없습니다. 장면 1개 = PDF 1쪽입니다 |
| (해석 확장) "깨짐"의 다른 원인 | 날짜·URL 같은 브라우저 머리글·바닥글, A4·Letter로 바뀐 용지, 빠진 이미지, 사라진 배경색도 깨짐으로 봅니다 |

### 1-3. 그대로 받아들이면 안 되는 점

| # | 해석 | 실측 결과 | 이 설계의 대응 |
|---|---|---|---|
| 1 | "인쇄하면 어디서든 16:9" | 대상을 "Microsoft Print to PDF"나 실제 프린터로 고르면 용지가 A4로 바뀝니다. `@page margin:0`이어도 날짜·URL·"1/12"가 장면 위에 찍힙니다. 이 PC에서는 새 프로필의 기본 대상이 "Microsoft Print to PDF"였습니다. OS 기본 프린터가 기본 대상이 되는 것으로 보이며(추정), 학생 PC마다 다를 수 있습니다[print-engine §대화상자] | 보장 범위를 **"Windows Chrome·Edge의 PDF로 저장, 여백 기본"**으로 한정하고(Q1 결정), 페이지 안에 인쇄 안내를 둡니다(§8-8). 대화상자를 거치지 않는 헤드리스 PDF 경로를 R0에서 시험합니다(§11-1) |
| 2 | "CSS로 잘림을 막을 수 있다" | CSS는 긴 문서를 고정 상자에 흘려 넣지 못합니다. 장면은 `overflow:hidden`이라 넘친 내용이 **소리 없이 사라집니다**. `overflow:auto` 안의 내용도 스크롤바 없이 잘립니다[print-engine §0, 함정 19] | 분할기(§6)가 넣고 측정하고 나눕니다. 하네스의 DOM 넘침 감사(§11)로 확인합니다 |
| 3 | "CDP로 PDF를 뽑아 보면 사람이 인쇄한 결과와 같다" | CDP는 화면 밖 `loading="lazy"` 이미지를 불러와 인쇄하지만, 실제 대화상자는 빼고 인쇄합니다. CSS `@page margin`은 CDP 여백 값은 이기지만 대화상자의 "최소·맞춤" 여백에는 집니다[print-engine §0] | 준비 게이트가 이미지를 미리 받게 하고(§8-2), 하네스는 남은 lazy를 실패로 봅니다. 대화상자 여백은 릴리스마다 사람이 확인합니다(§11-2 T12) |
| 4 | "빈칸 0" | 쪽 나눔 때문에 생긴 빈칸은 사라집니다. 하지만 장면 **안**의 여백은 남습니다. 문서 장면의 채움률(본문 상자 중 내용이 찬 비율)은 평균 0.72~0.83, 하위 10%가 0.30~0.54입니다. 원인은 큰 그림을 통째로 다음 장면으로 넘기는 것과 H2마다 새 장면을 여는 규칙입니다[paginator §0, §3-1]. **이 정책(H2 엄격 나눔, 그림 비분할, 블록 순서 고정) 아래에서는** 엄격하게 읽은 "빈칸 0"을 샘플로 달성할 수 없습니다[spec-impact §2]. 연속 흐름이나 그림을 남은 칸에 맞춰 줄이는 정책을 쓰면 수치가 달라집니다(미측정) | 운영 정의(Q1 결정)에서 "장면 안 여백은 레이아웃 규칙이 정한다"로 둡니다. 채움률은 리포트 지표로만 씁니다 |
| 5 | "모든 화면에서 16:9 장면" | 휴대폰 세로 화면에서 장면 배율은 0.28~0.29이고 본문이 약 4.5px로 보입니다. 손가락으로 확대하면 가로·세로 두 방향 스크롤이 생겨 WCAG 1.4.10(리플로, 좁은 화면에서 한 방향 스크롤만으로 읽혀야 한다는 기준)을 어깁니다[screen-ux §3] | 【R0 결정】 Q2: 문서 보기를 두지 않고 **휴대폰에서도 장면을 그대로 축소**합니다. 손가락 확대는 막지 않습니다(viewport에 `user-scalable=no`·`maximum-scale` 금지). WCAG 1.4.10 미충족은 **수용한 리스크**로 기록합니다(§7-6, §12). 인쇄는 그대로 16:9 |
| 6 | (참고) "세로로 긴 다이어그램도 한 장면에" | 16:9 장면 높이에 맞춰 줄이면 실효 글자(화면에 실제로 보이는 글자 크기)가 6~6.7px까지 떨어집니다. 문서마다 2~5개가 10px 미만입니다. 이 크기는 캔버스를 바꿔도 같습니다(캔버스 높이의 약 0.84%)[paginator §3-2] | 쪼개지 않고 줄여서 싣되, 리포트로 소스 수정 방향(나누기, LR 방향)을 안내합니다(Q9) |

### 1-4. 운영 정의 (Q1 결정)

R-B를 다음 네 조건으로 판정합니다(Q1-a: 추천안 4조건 그대로 결정). 하네스와 릴리스 완료 기준은 모두 이 정의를 씁니다.

| # | 조건 | 판정 방법 |
|---|---|---|
| ① | 장면 안 내용 잘림 0. 렌더러는 넘침을 **조용히 잘라 내지 않습니다**: 다음 장면으로 잇기 → 하한까지 축소 → 그래도 넘치면 눈에 보이는 "잘림" 띠 + 감사 실패(§4-3 원칙 5, §6-3 force) | DOM 감사: 모든 자손 상자가 장면 본문 상자 안에 있고, 장면과 그 안 스크롤 상자에 넘침이 없음, 잘림 띠 0(§11-2 T1) |
| ② | PDF 쪽 수 = 장면 수, 모든 쪽 960×540pt, 빈 쪽 0, 브라우저 머리글·바닥글 0 | PDF 사전 분석(§11-2 T2·T3) |
| ③ | 장면 안 여백은 브라우저가 아니라 레이아웃 규칙(템플릿, 분할 정책)이 정함 | 채움률 분포를 리포트에만 기록 |
| ④ | 그림·다이어그램은 쪼개지 않고 축소. 실효 글자가 10px 미만이면 리포트 **권장**, 10~12px이면 **참고** | 분할기 측정값(§6-5) |

보장 범위(Q1-b): **Windows의 Chrome·Edge(데스크톱) "PDF로 저장", 여백 "기본"**만 보장합니다. 학생 안내 문구는 **"Windows PC의 Chrome·Edge에서 저장하세요"**입니다(§8-8).

【R0 결정】 Q1-b는 추천안("macOS의 Chrome·Edge는 R0에서 확인한 뒤 보장 범위에 넣기")과 달리 **Windows만** 보장합니다. macOS는 R0에서도 확인하지 않고 보장하지 않으므로, R0의 macOS 확인 항목은 없앴습니다. 대가(수용한 리스크): Mac만 가진 학생에게는 보장되는 저장 경로가 없습니다. 헤드리스 PDF(§11-1)도 Windows의 Edge를 쓰므로 Mac에는 해당하지 않습니다. Mac의 Chrome·Edge에서 같은 결과가 나올 가능성은 있지만(엔진이 같음) 확인하지 않은 것이므로 "Mac에서 저장해도 된다"고 안내하지 않습니다.

여백 "없음·최소·맞춤"에서도 쪽 수는 지키도록 만들었지만(§8-1 zoom-fit 줄), 장면 아래쪽이 잘릴 위험과 머리글·바닥글이 남아 있어 보장하지 않습니다(미확인, §8-6). iOS·iPadOS의 Chrome·Edge(WebKit 엔진), Firefox·Safari, 휴대폰은 안내만 하고(보장 밖), Android의 인쇄는 미확인입니다(§8-7).

### 1-5. 용어 (처음 나오는 웹·인쇄 용어)

| 용어 | 뜻 (Unity 비유) |
|---|---|
| 논리 px, CSS px | 페이지 좌표의 단위. 화면 배율과 상관없이 장면 하나는 항상 1280×720 논리 px입니다. Unity의 Canvas Scaler "Reference Resolution"과 같은 개념입니다 |
| pt | 인쇄 단위. 1pt = 1/72in. CSS 1px = 0.75pt이므로 1280×720px는 960×540pt입니다 |
| `@page` | 인쇄할 때 용지 크기와 여백을 정하는 CSS 규칙 |
| `break-before: page` | "이 요소 앞에서 쪽을 넘겨라"는 인쇄용 CSS. 장면 사이에만 둡니다 |
| `print-color-adjust: exact` | 대화상자의 "배경 그래픽"이 꺼져 있어도 배경색·그라디언트를 그대로 인쇄하게 하는 CSS |
| `transform: scale(k)` / `zoom` | 요소를 k배로 그리는 두 방식. transform은 배치를 그대로 두고 그림만 키웁니다(Unity의 Transform.localScale). zoom은 배치 자체를 다시 계산합니다(해상도를 바꿔 UI를 다시 레이아웃하는 것과 비슷) |
| 분할기(paginator) | 기술 문서 블록을 장면에 하나씩 넣어 보고, 넘치면 다음 장면으로 보내거나 나누는 런타임 코드 |
| 채움률 | 장면 본문 상자의 높이 중 내용이 차지한 비율 |
| 실효 글자 | 축소·확대가 끝난 뒤 실제로 보이는 글자 크기 |
| 레터박스 | 화면 비율이 16:9가 아닐 때 장면 좌우·위아래에 남는 빈 띠 |
| 장면 축소 보기 | 이 설계의 하나뿐인 화면 보기. 창 크기와 상관없이 장면을 통째로 k배 줄이거나 키워서 보여 줍니다(Q2 결정, §7-2). Unity로 치면 Canvas Scaler "Scale With Screen Size" + Screen Match Mode "Expand"(배율 = 가로·세로 비율 중 작은 값이라 기준 해상도 전체가 늘 화면 안에 들어옴)와 같은 계산입니다 |
| 손가락 확대(pinch zoom) | 두 손가락(또는 트랙패드)으로 벌려 화면 일부를 크게 보는 동작. 페이지 배치는 바꾸지 않고 보이는 부분만 확대합니다. 브라우저 확대(Ctrl +)와는 다릅니다(§7-6) |
| 잘림 띠 | 어떤 방법으로도 장면에 안 들어간 내용이 있을 때 장면 아래에 붙는 빨간 "내용이 잘렸습니다 → 원문" 표시. 조용히 사라지는 것을 막는 최후 수단 |
| 준비 게이트 | 비동기 렌더(Markdown·Mermaid·분할·이미지)가 끝나기 전에는 인쇄해도 덱 대신 안내 문구 한 쪽만 나오게 하는 장치 |
| headless | 창을 띄우지 않고 실행하는 브라우저. 검사 도구가 씁니다 |
| DPR | 기기 픽셀 비율(devicePixelRatio). 125% 배율 화면이면 1.25 |

### 2-1. 캔버스

### 2-3. 화면 배율

배율 공식(Q2 결정): **모든 화면에서 k = min(vw / 1280, vh / 720)** 로 장면을 통째로 맞춰 축소·확대합니다. 남는 곳은 레터박스입니다. 구현에서는 장면 위아래 간격 gap = 16px를 빼서 `k = min(vw / 1280, (vh − 2·gap) / 720)`로 계산합니다(아래 표의 값). **하한은 없습니다.** 상한은 일반 보기 1.5, 전체 화면(발표 모드, gap 0)에는 상한이 없습니다. 모드 전환이 없으므로 같은 장면이 어느 화면에서나 같은 배치로 보이고, 크기만 다릅니다.

| 화면 (가정한 CSS 뷰포트) | k | 본문 16px의 실효 크기 | 비고 |
|---|---|---|---|
| FHD 창 최대화 (1920×945) | 1.268 | 20.3px | 좌우 레터박스 |
| FHD 전체 화면 (1920×1080) | 1.456 → 발표 모드 1.5 | 23.3~24px | 발표 모드는 정확히 화면을 채움 |
| FHD @125% (1536×729 @1.25) | 0.968 | 15.5 CSS / 19.4 물리 px | |

- 머리 = 왼쪽 장 이름(eyebrow) + **제목 + 도입 1~2줄**(`deck.slides[].lead`, 80자 안팎, 없으면 비움) + 오른쪽 탭 라벨·n/m. 높이는 내용에 따라 가변이고, 머리는 축소 대상이 아닙니다(축소는 본문 상자 안에서만).
- 본문 상자 = 머리 아래 ~ 바닥글(40) + 안전 여백(16) 위. 폭 1152, 좌우 64와 12칸 격자는 그대로입니다. 본문 위치는 머리를 잰 뒤 정합니다. 머리 높이 상한(넘으면 `info.overflow`에 기록해 리포트 권장)과 측정 순서(글꼴 로드 뒤 한 번)는 구현 중입니다.
- 【G8 결정】 본문 상자보다 내용이 짧으면 **항상 세로 가운데**입니다(포트폴리오 덱·발표 덱 공통). 채움률(내용 높이 ÷ 본문 상자 높이) 60% 미만은 `PFScene.report().info.notes[]`의 `low-fill`로만 내보내고 `audit`(빨간 배지)에는 넣지 않습니다(Q1-a ③의 구체화).
- 이 격자 그림과 §4-2 와이어프레임의 머리 높이 수치는 역사 기록으로 남기고 고치지 않습니다. 새 발표 덱의 장면 틀은 §13 머리의 【G 결정】 목록을 보세요.

### 3-2. 장면 마크업

```html
<main class="pf-deck" id="deck">
  <section class="pf-scene" id="s-12" data-pf-tpl="D1" data-pf-part="doc" aria-labelledby="s-12-t">
    <header class="pf-head"><p class="pf-crumb" id="s-12-t">크래프팅 › 기술 문서 › 3. 핵심 기능 <span class="pf-cont" data-pf-ui="cont" aria-hidden="true">(계속)</span></p></header>
    <div class="pf-body">…</div>
    <footer class="pf-foot"><span>홍길동 · 크래프팅 시스템</span><span class="pf-num"><span class="pf-n-screen">12 / 17</span><span class="pf-n-print">12 / 17</span></span></footer>
  </section>
  …
</main>
```

- 장면은 `.pf-deck` 바로 아래의 **형제**로만 둡니다. 장면 사이에 다른 요소를 두지 않습니다(덱 끝의 빈 `div`도 빈 쪽을 만듭니다)[print-engine 함정 9].
- `id="s-N"`은 장면 번호 앵커입니다. 문서 제목의 GitHub 슬러그 id(`#3-핵심-기능` 등)는 분할기가 그대로 옮겨 유지합니다[paginator §4].
- `data-pf-part`: `summary`(요약 장면) 또는 `doc`(기술 문서 부록과 P2 목차). 인쇄 범위 선택에 씁니다(§8-4).
- 바닥글 번호는 화면용(`.pf-n-screen`)과 인쇄용(`.pf-n-print`) 두 칸입니다. 인쇄 집합이 바뀌면(§8-4 "요약만") 키트가 인쇄용 번호를 다시 매기고, 인쇄 CSS는 화면용을 숨깁니다. 두 칸의 글자 수가 달라도 바닥글 띠는 고정 높이라 분할에 영향이 없습니다.
- `aria-labelledby`는 키트가 자동으로 붙입니다[screen-ux §5]. 이어지는 장면에서 반복되는 "(계속)"·반복 머리행은 `aria-hidden`으로 화면 낭독기에서 중복되지 않게 합니다.

### 3-3. 공통 규칙

1. 장면은 1280×720 고정, `overflow:hidden`입니다. 그래서 1장면 = 1쪽이 구조적으로 보장되고, 남은 위험은 "안에서 넘쳐 잘림" 하나뿐입니다. 이것은 분할기와 감사가 막고, 막지 못한 경우의 최후 수단도 "잘림"이 아니라 "이어짐 → 축소 → 보이는 잘림 띠" 순서로 정합니다(§4-3 원칙 5, §6-3 force). 측정 호스트가 없어도 이 순서는 보는 사람의 브라우저에서 실행되므로, 잘린 장면이 소리 없이 배포되지 않습니다.
2. 장면 안에서는 `vw`·`vh`·`dvh`, 뷰포트 폭 기준 `@media`, `position: fixed`·`sticky`를 쓰지 않습니다. 장면 안에서 크기에 따라 배치를 바꿔야 하면 **컨테이너 쿼리**(`@container pf-scene (…)`, 요소 자신의 상자 폭을 기준으로 하는 CSS)만 씁니다. 화면 보기가 장면 축소 하나뿐이라(Q2 결정) 컨테이너 폭은 화면·인쇄 모두 항상 1280입니다. 그래서 컨테이너 쿼리는 늘 같은 결과를 내고, 뷰포트 기준 규칙처럼 창 크기에 따라 장면 배치가 바뀌지 않습니다[screen-ux §2, §7].
3. 이어지는 장면 표기: 요약 장면은 제목 옆에 "1/2", 문서 장면은 머리줄에 "(계속)"을 붙입니다. 쪼개진 코드는 "다음 장에 계속 ↓ / 이어서 ↑", 쪼개진 표는 머리행을 반복하고 "표 이어서"를 표시합니다[paginator §2].
4. 장면 배경은 장면에 직접 칠합니다. Chrome·Safari는 `<body>` 배경을 인쇄하지 않습니다[print-engine §d].
5. URL은 클릭 링크와 함께 **글자로도** 보여 줍니다. 회사 보안 정책으로 외부 링크가 막힌 곳에서 PDF만 보는 경우가 있기 때문입니다[scene-design §1 G6].
6. "원문에서 자세히 →" 같은 페이지 안 이동은 화면에서는 장면 앵커, PDF에서는 "→ p.23" 같은 쪽 번호 글자로 바꿉니다. PDF 안 링크도 동작합니다(named destination)[paginator §4, spec-impact E8]. **대상 장면이 인쇄 집합 밖이면**("요약만" 인쇄) 쪽 번호 대신 배포 주소의 URL 글자(`…/project.html?p=<id>#<slug>`)로 바꿉니다(§6-6, §8-4).
7. 처음에 숨겨 두고 스크롤하면 나타나는 효과(투명 → 보임)는 PDF에서 빠질 위험이 있습니다(측정 안 함, 논리적 위험)[screen-ux §7]. 모든 요소의 기본 상태는 최종 상태이고, 모션은 화면 전용입니다. 기본 상태가 숨김인 등장 애니메이션(예: Tailwind `opacity-0` + `animation … forwards`)도 인쇄에서 최종 상태가 남도록 키트가 애니메이션 시간을 0으로 만듭니다(§8-1). 장면 안 그림은 `<img>`로 넣고 CSS `background-image: url()`은 쓰지 않습니다. 준비 게이트는 `<img>`만 기다리기 때문입니다(§9-4).

### 4-3. 용량 규칙과 변형 선택

**원칙**
1. **측정한 뒤 고릅니다.** 각 템플릿은 변형 목록을 우선순위대로 가지고 있습니다. 렌더러는 측정용 장면(§6-2)에 변형을 하나씩 넣어 보고, 넘치지 않고 채움이 기준 이상인 첫 변형을 씁니다. 다 안 되면 항목을 균형 있게 두 장면으로 나눕니다("1/2"). 교차 참조("원문에서 자세히")는 **더 긴 형태(URL 글자)로 측정**합니다. 그래야 인쇄 집합이 바뀌어 "→ p.23"과 URL 글자가 바뀌어도 넘치지 않습니다(§8-4).
2. 아래 글자 수 상한은 **빌드 리포트 경고용**입니다. 실제 결정은 측정이 합니다[scene-design §4-0].
3. 측정 전에 글꼴을 불러오고(`document.fonts.load` + `fonts.ready`), 이미지 크기를 알아야 합니다. Pretendard가 늦게 뜨면 한글 폭이 14.72px, 뜬 뒤에는 13.83px로 약 6% 달랐고, 이 차이만으로 넘침이 생겼습니다[scene-design §4-0].
4. 카드형 장면은 실측 채움 70~95%가 한계였습니다. 상한은 실측 최대치보다 10~15% 낮게 잡았습니다(가이드 "여백" 원칙)[scene-design §4-0].
5. 요약 데이터는 **잘라 내지 않고, 조용히 잘리게 두지도 않습니다.** 한 항목이 가장 넓은 변형에도 안 들어가면 렌더러가 다음 순서로 처리합니다(설계값, R1b 픽스처로 확인).
   1. **이어짐**: 그 항목의 필드(`what`·`how`·`why`, `problem`·`cause`·`solution`·`result`·`lesson`)를 분할기의 문단 분할(§6-4)로 나눠 "1/2"·"2/2" 장면으로 잇습니다. 필드 경계에서 먼저 나누고, 한 필드가 장면보다 길 때만 그 필드 안에서 줄 단위로 나눕니다.
   2. **축소**: 그래도 안 되면(한 필드의 한 줄 묶음이 장면보다 큰 경우 등) 그 장면만 글자 하한 15px까지 비례 축소합니다.
   3. **보이는 잘림 띠**: 그래도 넘치면 장면 본문 아래에 "내용이 잘렸습니다 → 원문: <URL 글자>" 띠(`.pf-clipped`, 화면·인쇄 모두 보임)를 붙이고 감사 실패로 기록합니다.

   어느 경우든 리포트 **필수**로 알립니다. 요약 문장은 빌드가 소스에서 만든 것이므로, 고칠 곳은 소스와 다시 빌드입니다(CLAUDE.md 원칙 4). 측정 호스트가 없어 빌드가 이 상황을 미리 못 잡아도(§11-1), 위 순서가 보는 사람의 브라우저에서 실행되므로 화면·PDF에서 내용이 소리 없이 사라지지 않습니다.

### 4-4. 템플릿 변형과 스타일의 관계

- 템플릿 **목록과 순서**는 렌더러 계약입니다. 프리셋이 바꿀 수 없습니다.
- 템플릿 **겉모습**의 닫힌 변형(표지 배치 `cover`, 바닥글 `footer`, 장면 배경 `scheme`, 제목 위치 `title-place` 등)은 스타일 프리셋의 변형 축입니다[02 §4-4].
- 변형 키워드는 렌더 전에 읽으므로 마크업을 바꾸는 변형도 깜빡임 없이 적용됩니다. 분할은 변형을 적용한 뒤에 합니다.

## 6. 기술 문서 분할기 (paginator)

### 6-1. 원칙

1. **보는 사람의 브라우저에서 페이지를 열 때 실행합니다.** 분할 결과는 글꼴·테마·문서에 따라 달라지므로 `data/`에 저장하지 않습니다. 저장하면 "사실만 담는다"는 원칙 1과 맞지 않고, 글꼴이 바뀌면 틀린 값이 됩니다[spec-impact §3 T4].
2. **문서를 바꾸지 않습니다.** 블록을 옮기고, 나누고, 줄이기만 합니다. 원문 전체 글자와 장면들을 이은 글자가 같아야 합니다(글자 보존 검사). 개발 중 목록 분할에서 항목이 사라지는 버그를 이 검사로 잡았습니다. 실제 구현에도 단언(assert)으로 남깁니다[paginator §6-6].
   - **비교에서 빼는 것**(명시 목록, 이 밖의 차이는 모두 실패): ① 원문 쪽 — 첫 H1(P1 표지에 있음), 건너뛴 문서 자체 "목차" H2 구간(§6-2 8번) ② 장면 쪽 — 반복 머리행, "표 이어서" caption, "(계속)"·"1/2", "다음 장에 계속 ↓ / 이어서 ↑", 머리줄·바닥글, 잘림 띠. 렌더러가 붙이는 UI 문구는 모두 `data-pf-ui` 속성을 달아 이 목록을 기계적으로 뺍니다(`cont` = 이어짐 표시·반복 머리행·"표 이어서", `chrome` = 머리줄·바닥글, `clip` = 잘림 띠).
3. **분할은 인쇄와 같은 k=1에서 합니다.** 화면 배율은 분할이 끝난 뒤에만 적용합니다(§7-1).
4. **결정적입니다.** 글꼴·테마·문서·Chromium 메이저 버전이 같으면 장면 경계가 같아야 합니다(§6-8).
5. 프로토타입은 `scratchpad\scene\paginator\site\paginator.js`(468줄)와 `scene-project.js`(373줄)입니다. R1c는 이것을 제품 코드로 옮기는 작업입니다.

### 6-2. 준비 단계 (순서 고정)

| # | 단계 | 내용 | 근거 |
|---|---|---|---|
| 1 | 스타일 | `applyStyle`(theme.css 가드, 변형 키워드)을 먼저 끝냅니다. 테마가 글꼴·밀도·크기를 바꾸기 때문입니다 | [spec-impact §3 T1] |
| 2 | 글꼴 | Pretendard 400/600/700/800과 D2Coding, 프리셋 제목 글꼴을 `document.fonts.load(…, '가…')`로 각각 불러오고 **각각 `.catch`** → `fonts.ready`, 상한 8초. catch가 없으면 글꼴 하나가 실패할 때 페이지 전체가 멈췄습니다. 글자 범위별 조각(unicode-range)으로 나뉜 글꼴은 표본 글자 대신 **실제 제목·본문 글자**로 `load`해 필요한 조각을 분할 전에 받습니다(설계값, 미검증) | [paginator §2] |
| 3 | Markdown | marked → 이미지 경로·GitHub 슬러그 id·`data-section` 처리(지금 `project.js`와 같은 규칙) | [paginator §1] |
| 4 | Mermaid | `mermaid.render(id, text)`로 측정용 컨테이너(body 바로 아래, 배율 1)에서 그려 SVG를 넣습니다. 장면 안에서 `mermaid.run()`을 제자리 실행하면 배율이 걸린 상태에서 라벨 폭을 재서 k<1이면 라벨이 잘렸습니다(k=0.833에서 10개 중 7개) | [screen-ux §2] |
| 5 | 코드 | hljs 하이라이트 → 줄 배열로 정규화(줄마다 열린 span을 다시 엶) | [paginator §2] |
| 6 | 이미지 크기 | `data`의 `media` 크기(w×h)로 `width`·`height` 속성을 넣어 다운로드를 기다리지 않습니다. **Q12 결정**: `/portfolio-build`가 이미지 파일 헤더에서 w×h를 읽어 `data/projects/*.json`의 `media`에 기록합니다(`schema.md`에 필드 추가, 설치 없이 PowerShell로 헤더를 읽음). 기록이 없으면 load 이벤트로 기다립니다. `img.decode()`는 가려진 창에서 끝나지 않으므로 쓰지 않습니다 | [print-engine §a, paginator §3-4] |
| 7 | 정규화 | 그림만 있는 `<p>` → figure, li 안의 글자 + 블록 혼합 → 글자 묶음을 블록으로, 표 → 첫 행 너비로 `<colgroup>` + `table-layout: fixed` | [paginator §2] |
| 8 | 구조 | 첫 H1 제거(제목은 P1에 있음), H2에 새 장면 표시, 첫 H2 앞의 도입부는 첫 장에 붙임, 문서 자체의 "목차" H2(제목이 목차·contents이고 본문이 페이지 안 링크 목록뿐)는 건너뜀(P2가 대신함) | [paginator §2, scene-design §4-2 D9] |
| 9 | 측정 | 블록 높이, 그림·도식 자연 크기, 도식의 `eff1 = 16 × 표시 폭 / viewBox 폭`(배율 1일 때 실효 글자) | [paginator §2] |

측정 장소는 `.pf-measure { position: fixed; left: 0; top: 0; width: 1px; height: 1px; overflow: hidden; visibility: hidden }` 안의 실제 `.pf-scene`(1280×720)입니다. 이렇게 하면 휴대폰에서 측정하는 동안 페이지 폭이 늘어나지 않습니다[paginator §2].

### 6-3. 알고리즘

```text
구간 = 강제 나눔 지점(H2, 단독 장면)마다 끊음
for 구간 g:
  if 앞 장면이 있고 g 전체 높이 ≤ 본문 상자의 40% and 앞 장면 남은 높이에 g가 통째로 들어감:
     g를 앞 장면에 이어 붙임(새 장면을 열지 않음), 리포트 참고 "짧은 장 이어 붙임"   # 짧은 H2 연속으로 거의 빈 장면이 이어지는 것을 막음(설계값, 미측정)
     continue
  S = paginate(g, 엄격)
  if |S| > 1 and fill(마지막 장면) < 0.3:                      # 꼬리가 거의 빈 장면
     S2 = paginate(복제본, 완화: soft = 0, keep = 0, rel = 0.6(프로토타입 매개변수), 인용 분할 허용)
     S3 = paginate(복제본, 완화 + 조임: 여백·행간 축소, 글자 크기는 그대로)
     장면 수가 줄어드는 첫 결과를 채택

paginate(q):
  cur = 새 장면; pend = []                     # 바로 앞에 놓인 제목들(다음 블록과 붙여야 함)
  while q:
    b = q.shift()
    if 강제 나눔(b) and cur에 내용 있음: pend를 데리고 새 장면
    if b가 제목:
       if H3·H4 and fill(cur) > 0.8: 새 장면                    # 부드러운 나눔(soft)
       붙이기; 넘치면 pend와 b를 함께 새 장면으로
       pend.push(b); continue
    if b가 hr and 빈 장면: 버림
    r = place(b, cur)
      all  → pend = []
      part → 새 장면(+ 구간 머리 "(계속)" 반복), q.unshift(나머지)
      none → 빈 장면이면 force(b), 아니면 pend를 데리고 새 장면, q.unshift(b)

place(b, s):
  그림·도식: 배율 1로 맞으면 all
      아니면 최소 배율 = 빈 장면 ? 0.05 : max(min(가독, fs), 0.85·fs)
        fs = 빈 장면에서 받을 배율, 가독 = 10px / eff1(도식), 이미지는 0.5
      0.01 단위 이분 탐색 → 맞으면 all, 안 맞으면 none          # 그림은 절대 쪼개지 않음
  맞으면 all
  쪼개기(블록별, §6-4). keep 규칙: 빈 장면이 아니고 빈 장면에는 통째로 들어가는 블록인데
         앞부분이 35% 미만이면 통째로 다음 장면

force(b, s)  (빈 장면에도 최소 단위가 안 들어갈 때. 프로토타입 동작 + 결과 정의)
  그림·도식: 0.05까지 축소 → 맞으면 끝(리포트 권장: 실효 글자)
  이미지가 든 표: 첫 행만 두고 이미지 축소, 나머지 행은 다음 장면
  상자·목록: 첫 자식만 두고 그 자식만 축소, 나머지 자식은 다음 장면
  그 밖(장면보다 높은 표 1행, 줄바꿈으로 장면을 넘는 코드 원문 1줄 등): zoom 0.3까지 이분 탐색 축소
  그래도 fits 실패 → 잘림 띠(.pf-clipped "내용이 잘렸습니다 → 원문: <URL 글자>") + 감사 실패 + 리포트 필수
  축소 후 실효 글자가 하한(본문 15px·코드 13px) 미만이면 리포트 필수   # 실제 4문서에서 force 0건[paginator §3-1]

fits(s) = body.scrollHeight ≤ clientHeight
        ∧ scrollWidth ≤ clientWidth
        ∧ 마지막 자식.bottom ≤ body.bottom − 1(slack)     # 안전 여백 16은 본문 상자 590·544에 이미 들어 있음
verify  = 모든 자손 rect ⊂ 본문 상자(조상이 잘라 주는 요소 제외)
        ∧ pre·td 안 가로 스크롤 없음
        ∧ 글자 보존(원문 == 장면 합. 비교 제외 목록은 §6-1 원칙 2)
```

**H2마다 새 장면(엄격)을 고른 이유**: 연속 흐름보다 장면이 3~7% 늘고 평균 채움이 6~11%p 낮아집니다[paginator §3-2]. 그래도 가이드의 "한 화면 = 한 메시지"(장 하나를 한 묶음으로)와 목차·딥링크의 안정성을 우선합니다. "남은 공간이 45% 미만일 때만 새 장면" 정책은 장면 수 차이가 ±3이라 얻는 것이 작았습니다[scene-design §4-2 D1]. 다만 2~3줄짜리 H2가 많은 학생 문서는 엄격 규칙만으로는 거의 빈 장면이 연달아 생겨 유지관리자가 말한 "빈칸"이 그대로 나타나므로, 장 전체가 본문 상자의 40% 이하이고 앞 장면에 통째로 들어가면 앞 장면에 이어 붙입니다(위 알고리즘 첫 줄. 샘플 4편에서 몇 번 일어나는지는 미측정, R1c에서 기록).

- 단락 + 좁은 도식 나란히(D11), 장 표지(D4): 효과 미확인이라 후속 선택으로 둡니다.

### 6-5. 그림·다이어그램 축소와 가독성

- 맞춤 배율 = min(1, 본문 폭 / w, (본문 높이 − 앞 설명 − 캡션) / h). 확대하지 않습니다.
- 실효 글자 = eff1 × 배율. **10px 미만이면 리포트 권장, 10~12px이면 참고**(Q9). 기준점: 배율 0.6 ≈ 16px × 0.6 = 9.6px[spec-impact N8].
- 빈 장면에서도 안 들어가면 0.05까지 줄이고 경고합니다. 이 경우는 실제 4문서에서 0건이었습니다(강제 0)[paginator §3-1].
- **Mermaid 기본 설정을 촘촘하게** 바꿉니다: `flowchart:{nodeSpacing:28, rankSpacing:32}`, `sequence:{mirrorActors:false, messageMargin:22}`. 26개 중 11px 미만이 14개 → 9개로 줄었습니다. 학생 소스는 바꾸지 않고, 문서 안 `%%{init}%%`이 있으면 그것이 우선합니다(format/03 원칙)[scene-design §6-3].
- 남는 작은 도식은 **소스에서** 고칩니다(LR 방향으로 바꾸기, 둘로 나누기). 리포트는 방향만 알리고 Mermaid 코드를 대신 쓰지 않습니다(format/03 원칙). 샘플 기준으로 남는 9개: Tidy 3.3·4.2, 크래프팅 클래스 도식, 액션 플랫포머 2.1·3.2·4.2·5.2, 이그드라실 3.1·3.7[scene-design §6-3].
- 호스트 없이 빌드 리포트를 만들 때의 휴리스틱: Mermaid의 자연 높이가 약 966px(16px 글자 기준, 세로 약 12단 이상)를 넘으면 10px 미만이 됩니다[paginator §8]. 노드 수·방향으로 이 높이를 추정하는 기준은 R1에서 보정합니다(미확인).
- 90도 회전 장면은 PDF에서는 읽히지만(예: 549×1070 → 회전 시 13px) 화면에서 어색해서 기본값으로 두지 않습니다[scene-design §6-3].

### 6-6. 목차·앵커·교차 참조

- **제목 → 장면**: `id` 요소를 복제하지 않고 그대로 옮기므로 GitHub 슬러그 id가 유지됩니다. 분할 뒷부분의 복제본은 id를 지웁니다. 분할이 끝나면 `anchors{id → 장면 번호}`를 만듭니다[paginator §4].
- **P2 목차**: H2·H3를 2단 목록으로 나열하고 쪽 번호를 답니다. 번호 자리를 고정폭 공백으로 먼저 비워 두고 분할한 뒤 채웁니다. 그래서 목차 길이가 번호에 따라 바뀌지 않습니다. 항목 15/37/54/36개 → 목차 장면 1/1/2/1개[paginator §4].
- **"원문에서 자세히 →"(`highlights[].section`)**: project.js와 같은 제목 정규화 규칙으로 id를 찾고, 화면에서는 앵커, PDF에서는 "→ p.23" 글자로 바꿉니다. 4문서 모두 PDF에서 맞는 쪽으로 이동했습니다[paginator §4].
- **인쇄 집합이 바뀔 때**(§8-4 "요약만"): 키트가 인쇄용 바닥글 번호, 목차 쪽 번호, "→ p.n"을 **인쇄되는 장면만 세어 다시 계산**합니다. 대상 장면이 인쇄 집합 밖이면 "→ p.n" 대신 배포 주소의 URL 글자(`…/project.html?p=<id>#<slug>`)를 씁니다. 주소는 `location`에서 만들고, localhost·`file:`에서 인쇄하면 HUD가 "배포된 주소(github.io)에서 저장해야 PDF 속 링크가 맞습니다"라고 알립니다.
- **PDF 책갈피(개요)**: CDP `generateDocumentOutline`을 켜면 28개가 생겼습니다. Ctrl+P "PDF로 저장"에서 생기는지는 미확인입니다[paginator §4]. 헤드리스 PDF(§11-1)의 CDP 경로에서만 보장하며, 단계는 P3입니다. 헤드리스 CLI(`--print-to-pdf`)에서 책갈피가 생기는지는 미확인입니다.

**이 설계의 처리**
- 재분할은 `PFScene.track(repaginate())`로 등록합니다. 그동안 준비 게이트가 다시 닫히므로, 재분할 0.3~1초 사이에 인쇄해도 어긋난 PDF 대신 안내 한 쪽이 나옵니다(§8-2).
- 글꼴 로드가 끝내 실패하면 `data-pf-font="fallback"`을 붙이고 HUD에 "글꼴을 불러오지 못해 대체 글꼴로 나뉘었습니다. 인쇄는 정상이지만 장면 경계가 다를 수 있습니다"를 띄웁니다. 인쇄는 막지 않습니다. 대체 글꼴로도 넘침 0이 실측됐기 때문입니다.
- 남은 위험
  - Pretendard CSS가 `local('Pretendard')`를 먼저 쓰므로, 설치본이 있는 PC는 결과가 다를 수 있습니다(미확인). R0에서 확인하고, 필요하면 렌더러가 `local()` 없는 `@font-face`를 직접 선언합니다.
  - Pretendard를 dynamic-subset(글자 범위별 조각 로드)으로 바꾸면 측정 시점과 조각 로드가 엇갈릴 수 있습니다(미확인)[spec-impact §8]. R0 스파이크에서 결정하고, 결정 전에는 지금의 정적 CSS를 유지합니다.
  - Chromium 메이저 버전(약 4주마다 바뀜)이 바뀌면 줄바꿈이 달라져 쪽 수가 바뀔 수 있습니다(미확인). 골든 장면 나눔 JSON과 PDF 단언으로 자동 회귀 검사하고, 달라졌을 때만 다시 기록합니다(§11-3).
  - 사용자가 브라우저 확대(Ctrl±)를 한 상태에서 인쇄하면, 분할 시점과 인쇄 시점의 줄바꿈이 달라 장면이 넘칠 수 있습니다(미확인). 안전 여백 16px의 효과도 측정하지 않았으므로 **R0 스파이크**(67~200% 확대 후 인쇄)로 확인합니다.

### 6-9. 알려진 한계

- `::marker`(목록 번호)는 rect로 검사할 수 없어 감사가 잡지 못합니다. 두 자리 번호가 상자 밖으로 나가 잘렸던 문제는 `ol { padding-left: 2.4em }`로 막았습니다[paginator §6-5].
- 표 안 이미지 행이 장면보다 높으면 이미지를 줄입니다. 실제로 나온 경우는 0건입니다[paginator §7].
- 원문에 이미 "목차"가 있으면 생성 목차와 겹칩니다. §6-2 8번 규칙으로 하나를 숨기지만, 판정 규칙이 맞지 않는 형식(표로 만든 목차 등)은 미확인입니다.
- 분할 품질 위험: 중첩 목록, 긴 셀, 문서 속 HTML, `<details>`[spec-impact §3 "§12 새 리스크"]. R1c 픽스처에 넣습니다.

| 배치 | 분할(k=1)과 **완전히 같음**. 논리 높이 흔들림 0 | 줄바꿈을 다시 계산함. 장면 아래 끝이 k=0.75에서 +10.7 / −3.1px 흔들림 | [screen-ux §2 E1f] |
| 실제 문서에서 넘침 | 0 | k=0.5·0.73에서 문서당 7~21장면 넘침(최대 65px. 어느 배율의 값인지는 보고서에 구분 없음). **k ≥ 1.1에서는 0** | [paginator §5] |
| 글자 선명도 | 원래 크기 렌더 대비 중간 톤 픽셀 +15~34%. `will-change`를 붙이면 DPR 1에서 흐려짐 | 원래 크기 렌더와 **md5 동일** | [screen-ux §2] |
| 클릭 위치·텍스트 선택·IntersectionObserver·앵커·`@container` | 정상 | 정상 | [screen-ux §2] |
| Mermaid `run()` 제자리 실행 | 라벨이 잘림 | 라벨이 잘림 | [screen-ux §2] → §6-2의 `render()`로 해결 |
| 장면 안 `<dialog>` | 정상 | 배율만큼 작아짐 | [screen-ux §2] → 대화상자는 body 바로 아래에만 둠 |
| 인쇄 | `transform:none !important`로 되돌림(960×540) | `zoom:1 !important`(960×540) | [print-engine 함정 13] |

**결정**
1. **기본은 `transform`** 입니다. "분할한 그대로 화면에 보인다 = 인쇄된다"를 구조로 보장하기 때문입니다. 선명도 차이는 품질 문제이고, 넘침은 내용이 사라지는 정확성 문제라서 정확성을 우선합니다.
2. **R0 스파이크**: k ≥ 1.1(FHD 최대화 1.268, 전체 화면 1.456~1.5, QHD)에서만 `zoom`을 쓰는 혼합 방식을 검증합니다. 통과 기준은 샘플 4편 × k ∈ {1.1, 1.268, 1.5}에서 실행 중 넘침 감시(§7-2) 0건, 하네스 T1 통과입니다. 통과하면 혼합으로, 아니면 transform만 씁니다. 이 결정은 구현자가 측정으로 하며 유지관리자 질문이 아닙니다.
3. `will-change`는 쓰지 않습니다.

**transform 구현** — 장면은 형제 구조 그대로 두고, 바깥 여백으로 크기 차이를 보정합니다.

```css
@media screen {
  .pf-deck            { display: flex; flex-direction: column; align-items: center;
                        gap: var(--pf-gap); padding: var(--pf-gap) 0; }
  .pf-deck > .pf-scene { flex: none; transform: scale(var(--pf-k)); transform-origin: 0 0;
                        margin: 0 calc(1280px * (var(--pf-k) - 1)) calc(720px * (var(--pf-k) - 1)) 0;
                        box-shadow: 0 2px 14px rgba(20, 22, 30, .14); }
}
```

- 바깥 여백 상자의 크기가 1280k × 720k가 되므로 가운데 정렬과 장면 간격이 배율을 따라갑니다. 휴대폰(k 0.28~0.29)에서도 레이아웃 폭이 1280k(375px 화면이면 약 375px)라 가로 넘침이 생기지 않습니다(계산값, T9로 확인).
- 화면 보기가 하나뿐이므로(Q2 결정) 옛 모드 클래스(`html.pf-mode-scene`·`pf-mode-reflow`·`pf-fit-width`)는 없앴습니다. 선택자를 `.pf-deck > .pf-scene`으로 좁혀, 측정용 장면(`.pf-measure` 안, §6-2)에는 배율이 걸리지 않게 합니다.
- 분할기 프로토타입은 장면을 `.scene-frame`으로 감싸는 방식으로 검증했고[paginator §1], 인쇄 레시피는 감싸지 않은 형제 구조로 검증했습니다[print-engine §a]. 위 "형제 + 여백 보정" 조합 자체는 **미확인**이며 R0에서 하네스로 확인합니다. 실패하면 감싸개 방식으로 바꾸고 인쇄 규칙의 선택자만 `.pf-frame`으로 옮깁니다.
- 측정은 `offsetHeight`·`scrollHeight`(배율과 무관한 논리 px) 또는 `getBoundingClientRect()/k`로 합니다. zoom이 걸린 요소 자신의 `offsetTop`은 0으로 나왔으므로 스크롤 위치는 `scrollIntoView`나 gBCR + scrollY로 계산합니다[screen-ux §2].

### 7-2. 배율 결정: 장면 축소 단일 모드

【R0 결정】 Q2: 추천안의 세 가지 보기(장면 맞춤 / 마우스 데스크톱 폭 맞춤 / 좁은 화면 문서 보기)와 그 사이의 모드 전환을 **모두 없애고**, 모든 화면에서 장면을 통째로 맞춰 축소하는 보기 하나만 둡니다. 얻는 것: 화면 = PDF가 어느 기기에서나 같고, 모드 전환 로직·문서 보기 CSS·그 검사가 사라져 구현과 검증이 작아집니다(R1e 1.5~2.5일 → 0.5~1일). 감수하는 것: 휴대폰 세로 본문 약 4.5px, WCAG 1.4.10 미충족, 브라우저 확대가 장면을 키우지 못할 수 있음(1.4.4)입니다(§7-6, §12).

```js
function fit() {                                      // 로드와 resize 때마다. 모드 판단 없음
  const vw = root.clientWidth, vh = innerHeight, gap = presenting ? 0 : 16;   // 발표 모드는 간격 0
  let k = Math.min(vw / 1280, (vh - 2 * gap) / 720);  // = min(vw/1280, vh/720)에서 장면 위아래 간격을 뺀 값. 하한 없음
  if (!presenting) k = Math.min(k, 1.5);              // 일반 보기 상한 1.5, 발표 모드는 상한 없음
  // 브라우저 확대 보완안(§7-6, 제안)이 R0에서 채택되면 여기서 k에 HUD 배수를 곱하거나 k 하한을 둡니다
  root.style.setProperty('--pf-k', String(k));
  if (!first) realign(scenes[cur]);                   // 처음 한 번은 다시 맞추지 않음(딥 링크 보호)
}
```

- **딥 링크 버그 교훈**: 처음 배율을 정할 때 "현재 장면 다시 맞추기"를 실행하면 해시 이동을 2ms 뒤에 덮어썼습니다. 그래서 다시 맞추기는 처음 배율을 정한 **뒤의 resize에서만** 합니다[screen-ux §4].
- 장면 높이는 뷰포트 높이를 넘지 않으므로(k를 높이로도 제한) `go(i)`는 장면을 가운데에 맞춥니다(§7-4). 브라우저 확대 보완안(§7-6)이 채택되어 장면이 뷰포트보다 커질 때만 위쪽에 맞춥니다.
- **실행 중 넘침 감시**(설계안, 미측정): ResizeObserver로 장면 본문의 넘침을 감시합니다. 사용자가 브라우저 최소 글꼴 크기를 올렸거나 글자 간격을 재정의하면 빽빽한 장면이 128~281px 넘쳤습니다[screen-ux §5]. 넘침이 생기면 `PFScene.track(repaginate())`로 **다시 나눕니다.** 그러면 화면과 인쇄가 모두 그 사용자의 글꼴 설정으로 다시 나뉘어, 화면만 피하고 PDF는 잘린 채 남는 일이 없습니다. 다시 나눠도 넘치면 §4-3 원칙 5·§6-3 force 순서를 따릅니다. 반복 재분할을 막기 위해 같은 원인(글꼴 설정)으로는 한 번만 다시 나눕니다.
- **감사 배지**: localhost·127.0.0.1에서 열면 HUD에 `PFScene.audit()` 결과 개수를 빨간 배지로 늘 보여 줍니다(0이면 숨김). 학생·Claude가 미리보기에서 잘림을 바로 봅니다.
- 회전 안내: 돌렸을 때의 k가 지금보다 크고 0.75 이상일 때만 "가로로 돌리면 더 크게 보입니다" 안내를 띄웁니다(iPad 세로 0.641 → 가로 0.922라 띄움, iPhone은 가로도 0.43이라 안 띄움)[screen-ux §3].

**좁은 화면(휴대폰·태블릿 세로·좁은 창)**
- 같은 장면을 작게 세로로 이어 보여 줍니다. 장면 배치·이어짐 표시·바닥글 쪽 번호가 데스크톱·PDF와 똑같습니다.
- 손가락 확대(pinch zoom)로 읽습니다. `<meta name="viewport" content="width=device-width, initial-scale=1">`만 쓰고 **`user-scalable=no`·`maximum-scale`은 넣지 않습니다**(§9-3). 확대한 뒤에는 가로·세로 두 방향 스크롤이 생기며, 이것이 WCAG 1.4.10 미충족의 내용입니다(수용한 리스크, §7-6).
- 상단바는 어떤 화면에서도 두지 않습니다(HUD로 대체, §5-1).
- 인쇄는 화면 상태와 상관없이 16:9입니다. 옛 문서 보기 상태의 375px에서 인쇄해도 데스크톱과 같은 24쪽이 나왔습니다[screen-ux §0]. 축소 장면 상태의 375px 인쇄는 인쇄 CSS가 transform을 되돌리므로 같을 것으로 보지만 미확인입니다(T9).

### 7-3. HUD (화면 조작 막대)

| 요소 | 동작 |
|---|---|
| 이전 · "n / N" · 다음 | 장면 단위 이동 |
| 전체 화면 | Fullscreen API + 발표 모드(§7-5, R1.5부터). 데스크톱에서 정확한 16:9를 얻는 유일한 경로입니다 |
| 확대 [−] 배수 [+] (**제안**, R0 스파이크에서 채택 여부 결정) | 브라우저 확대 보완안 ①(§7-6). k에 배수 m(1.0~2.0)을 곱해 장면을 키우고, 장면이 화면보다 커지면 스크롤로 봅니다. 키보드로 쓸 수 있고, 선택은 `localStorage`에 기억(읽기·쓰기 모두 try/catch). 인쇄에는 영향 없음 |
| PDF로 저장 ("PDF n쪽") | 준비 게이트를 기다린 뒤 `print()`. 대기 중에는 "이미지 3/12 불러오는 중". 20초가 지나면(`timeout`) "아직 다 그리지 못했습니다" 경고와 **[그래도 인쇄]** 버튼을 보여 줌(§8-2) |
| 인쇄 범위 (project.html) | 전체 / 요약만(§8-4). 쪽 수 표시가 함께 바뀜 |
| 경고 | 대체 글꼴 분할(§6-8), 넘침 감시로 다시 나눔(§7-2), 잘림 띠가 있는 장면, localhost에서 인쇄 시 링크 주소 경고(§6-6) |
| 감사 배지 (localhost만) | `PFScene.audit()` 문제 개수를 빨간 배지로 상시 표시(§7-2) |

- 위치: 레터박스가 64px 이상이면 그 안에 세로로 둡니다(FHD 최대화·1366·125%·150%·21:9). 더 좁으면(휴대폰·태블릿 세로·가로가 꽉 차는 창) 작은 알약 모양으로 접어 오른쪽 아래에 두고 `html.pf-hud-pill`을 붙입니다(§8-1의 `scroll-padding-bottom`). 레터박스가 없는 화면에서 HUD가 장면 오른쪽 아래 내용을 가렸습니다[screen-ux §3].
- 옛 [장면 보기 ↔ 문서 보기] 전환 버튼은 Q2 결정으로 없앴습니다.
- DOM에서는 "본문으로 건너뛰기" 링크 바로 다음, 덱 앞에 둡니다. 지금처럼 body 끝에 두면 Tab 순서상 맨 뒤가 됩니다[screen-ux §5].
- 인쇄에서는 숨깁니다(`.pf-hud`).

### 7-4. 내비게이션

- **CSS scroll-snap은 기본으로 끕니다**[screen-ux §4].
  - 휠 1칸이 원래 장면으로 되돌아갔습니다(proximity·mandatory 모두).
  - proximity에서는 장면 사이 어중간한 위치에 멈췄습니다.
  - 뒤로 가기 스크롤 복원이 깨졌습니다(proximity에서 y 929 → 0).
  - 휠 결과는 headless 합성 휠 이벤트 기준이며, 실제 마우스 휠·트랙패드 관성은 미확인입니다.
- 키: PageDown·Space·→ = 다음, PageUp·Shift+Space·← = 이전, Home·End = 처음·끝. ↑↓는 브라우저 기본 동작에 맡깁니다. 입력란, 가로 스크롤이 있는 요소, 열린 dialog 안에서는 키를 가로채지 않습니다. 키트 이동은 장면 정렬 오차 0이었습니다(기본 PageDown은 103 → 412px씩 어긋남)[screen-ux §4].
- `go(i)`: `scrollIntoView({block:'center'})`(확대 보완안으로 장면이 뷰포트보다 클 때만 `'start'`) → `focus({preventScroll:true})` → `history.replaceState(…, '#s-' + n)`. 기록 항목을 늘리지 않습니다. 본문 링크 클릭은 원래대로 기록에 남깁니다. 부드러운 스크롤은 `prefers-reduced-motion: no-preference`일 때만 씁니다.
- 딥 링크: 준비 게이트가 열린 뒤 `#s-12`, 제목 id(비동기 Mermaid 장면 안 제목 포함)로 이동합니다. 장면 높이가 고정이라 늦게 그려지는 내용이 위치를 밀지 않습니다. 실측에서 모두 정확했습니다[screen-ux §4].
- Tab 이동: `focusin`에서 포커스가 간 장면이 화면에 통째로 보이게 맞춥니다. 6번 모두 성공[screen-ux §4].

### 7-5. 발표 모드

- 단계: R1.5(Q16 결정, R1-core에는 없음).
- 전체 화면 + 장면 간격 0 + 배율 상한 없음(FHD 전체 화면이면 정확히 1920×1080을 채움) + mandatory snap(발표 모드에서만). F 키로 켜고 끕니다[screen-ux §3·§4].
- 4:3 프로젝터(1024×768)에서는 코드가 약 11px라 도식·코드 장면이 약합니다. 요약 장면 중심으로 발표하고, P2 목차의 쪽 번호로 질문받은 장면에 바로 갑니다[scene-design §7].
- 발표 메모는 v1에 넣지 않습니다. 넣는다면 학생이 직접 쓴 것만 씁니다(원칙 1·2)[spec-impact §4].

### 7-6. 접근성

해석은 법적·인증 판단이 아닙니다.

【R0 결정】 Q2(장면 축소 단일 모드)로 옛 설계의 접근성 대책이던 **문서 보기("적합한 대체 버전")가 없어졌습니다.** 그래서 1.4.10은 **수용한 리스크**로 기록하고, 1.4.4는 R0에서 보완안을 정할 때까지 열린 문제로 둡니다(보완안을 하나도 채택하지 않으면 1.4.4도 수용한 리스크가 됩니다).
- **WCAG 1.4.10 리플로 — 미충족(수용).** 폭 360~375px 휴대폰에서 장면은 통째로 축소되어 본문이 약 4.5~4.7px입니다(§2-3). 손가락 확대로 읽으면 가로·세로 두 방향 스크롤이 필요합니다. 대응은 손가락 확대를 막지 않는 것(viewport에 `user-scalable=no`·`maximum-scale` 금지), 가로 넘침 0(확대 전 화면에서 가로 스크롤 없음, T9), 회전 안내, PC에서 PDF 받기 안내입니다.
- **WCAG 1.4.4 글자 크기 조정 — 문제 가능(열린 문제, R0에서 보완안 결정).** 데스크톱에서 브라우저 확대(Ctrl +)를 하면 CSS 뷰포트가 줄어 k가 다시 계산되므로, 장면의 실제 크기가 그대로일 수 있습니다. 옛 모드 규칙에서 FHD 110~150% 확대의 실제 글자는 ×0.99~1.00이었고(실측)[screen-ux §5], 단일 모드에서는 문서 보기로 바뀌는 지점이 없으므로 모든 확대율에서 같을 것으로 봅니다(계산값, 미확인). 손가락·트랙패드 확대는 레이아웃 뷰포트를 바꾸지 않아 k가 그대로이므로 실제로 커질 것으로 보지만 데스크톱 실동작은 미확인입니다.

### 7-7. 성능

- 100장면(GIF 장면 20, Mermaid 10개) 준비 완료 약 0.8초, 스크롤 p95 34~49ms, 메모리(headless 프로세스 합) 742MB로 지금 렌더러 상세 페이지(764MB)와 비슷했습니다[screen-ux §6]. 실기기 수치는 미확인입니다.
- 이미지
  - 화면에서는 `loading="lazy" decoding="async"`로 시작합니다. 1-action-platformer는 GIF만 49MB라 폰에서 중요합니다[screen-ux §6].
  - **데스크톱 기기**(`pointer: fine`이고 데이터 절약 `navigator.connection.saveData`가 아님)에서는 창 크기와 상관없이 준비가 끝난 뒤 lazy를 eager로 바꿔 미리 받습니다. 실제 인쇄 대화상자가 화면 밖 lazy 이미지를 빼고 인쇄하기 때문입니다(§8-3). 대역폭을 더 쓰는 대신 Ctrl+P 경로의 R-B를 지킵니다. 창 크기·배율이 아니라 기기로 정하므로, 데스크톱에서 창을 좁혀도 Ctrl+P 첫 시도가 "아직 그리는 중" 한 쪽이 되지 않습니다.
  - 화면 보기가 하나뿐이라 성능은 모드에 따라 달라지지 않습니다. 휴대폰에서도 같은 장면 DOM을 그리고 transform만 다릅니다.
  - 폰·태블릿(`pointer: coarse`)과 데이터 절약 모드에서는 lazy를 유지합니다. 이 상태에서 인쇄하면 §8-2의 인쇄 직전 확인이 안내를 띄웁니다.
- Mermaid는 로드 직후 측정용 컨테이너에서 차례대로 그립니다(10개 약 0.4초)[screen-ux §6].

## 8. 인쇄 레시피 (PDF = 화면)

인쇄 입장은 하나입니다. **PDF는 화면과 같은 16:9 장면을 한 쪽씩 담고, 배경까지 그대로 저장합니다**(Q10 결정: `print-color-adjust: exact`, 다크 프리셋은 다크로 인쇄). 인쇄 전용 밝은 팔레트는 v1에 없습니다. R1에는 밝은 인쇄 **예약 훅**만 넣습니다: `print: screen|light` 화이트리스트 자리, Mermaid 인쇄용 두 번째 렌더 자리, validate의 플래그 구간(R1g, R1-core)[02 §6-6]. 밝은 인쇄 자체는 필요하면 P3입니다. 이 절의 CSS·JS는 공용 장면 키트(`assets/scene-kit.css`, `assets/scene-kit.js`)에 들어가고, 고정 렌더러와 `/portfolio-custom`이 같은 파일을 씁니다.

### 8-2. 준비 게이트 (`scene-kit.js` 앞부분, `<head>`에서 동기 로드)

```js
// 로드 즉시 data-pf-ready="no". 비동기 작업은 PFScene.track(promise)로 등록합니다.
//   "no" = 그리는 중(인쇄하면 안내 한 쪽) | "yes" = 인쇄 가능
//   "timeout" = 20초가 지났는데 아직 그리는 중(인쇄하면 여전히 안내 한 쪽, HUD 경고 + [그래도 인쇄]. 끝나면 "yes"로 회복. 하네스는 실패)
(() => {
  const root = document.documentElement, jobs = [];
  let gen = 0, t, mounted;
  root.dataset.pfReady = 'no';
  const EAGER = matchMedia('(pointer: fine)').matches &&               // 데스크톱 기기면 창 크기와 상관없이 미리 받음(§7-7)
                !(navigator.connection && navigator.connection.saveData);
  const tick = () => new Promise((r) => setTimeout(r, 0));          // rAF 금지: 가려진 창에서 멈춤(실측)
  const loaded = (i) => i.complete ? null : new Promise((r) => {     // decode() 금지: 가려진 창에서 안 끝남(실측)
    i.addEventListener('load', r, { once: true }); i.addEventListener('error', r, { once: true }); });
  async function settle() {
    const my = ++gen;
    if (root.dataset.pfReady === 'yes') root.dataset.pfReady = 'no';  // timeout 표시는 끝날 때까지 유지
    for (let n = -1; n !== jobs.length;) { n = jobs.length; await Promise.allSettled(jobs); }  // 도중 등록분까지(mount 대기 포함)
    if (EAGER) document.querySelectorAll('img[loading="lazy"]').forEach((i) => { i.loading = 'eager'; });
    await Promise.all([...document.querySelectorAll('img:not([loading="lazy"])')].map(loaded));
    if (document.fonts) await Promise.race([document.fonts.ready, new Promise((r) => setTimeout(r, 3000))]);
    await tick();
    if (my === gen) root.dataset.pfReady = 'yes';                       // timeout 뒤에 끝나도 반드시 회복
  }
  const schedule = () => { clearTimeout(t); t = setTimeout(settle, 0); };
  // mount()가 한 번 불릴 때까지 게이트를 닫아 둠: fetch만 track하고 React commit·mount 전에 "yes"가 되는 경쟁을 막음
  jobs.push(new Promise((r) => { mounted = r; }));
  addEventListener('load', schedule);
  addEventListener('beforeprint', () => {                               // 폰·데이터 절약(lazy 유지)에서 인쇄할 때
    const pending = [...document.images].filter((i) => !i.complete);    // 아직 안 받은 lazy 이미지 포함
    if (pending.length) { root.dataset.pfReady = 'no';                  // 이번 인쇄는 안내 한 쪽
      document.querySelectorAll('img[loading="lazy"]').forEach((i) => { i.loading = 'eager'; });
      schedule(); }                                                     // 다음 인쇄를 위해 받기 시작
  });
  addEventListener('afterprint', () => { delete root.dataset.pfPrintAnyway; });
  setTimeout(() => { if (root.dataset.pfReady === 'no') root.dataset.pfReady = 'timeout'; }, 20000);
  window.PFScene = Object.assign(window.PFScene || {}, {
    track(p) { jobs.push(Promise.resolve(p).catch((e) => console.warn('[pf-scene] 작업 실패:', e))); schedule(); return p; },
    get ready() { return root.dataset.pfReady; },
    _mounted() { mounted(); schedule(); },                              // mount() 안에서 한 번 호출
    printAnyway() { root.dataset.pfPrintAnyway = ''; print(); },        // HUD [그래도 인쇄]
  });
})();
```

- 출처: [print-engine §a]의 `pf-ready.js`(40줄, `scene\print-recipe\recipe\pf-ready.js`). 바꾼 점은 네 가지입니다. ① lazy → eager 전환을 **데스크톱 기기**에서만 합니다(§7-7). ② `beforeprint` 확인을 더했습니다. ③ **timeout 고착 버그를 고쳤습니다.** 원본(그리고 이 문서의 이전 판)은 끝에서 `pfReady !== 'timeout'`을 확인해, 20초가 지난 뒤 이미지 로드가 끝나도 영원히 `yes`가 되지 않았고(그러면 [PDF로 저장]이 영구 대기), 20초~완료 사이의 Ctrl+P는 이미지가 빠진 덱을 인쇄했습니다. 시뮬레이션(timeout 200ms, 이미지 450ms)에서 `t=500ms ready=timeout imgComplete=true`, `t=2000ms ready=timeout`이었습니다[critic-final `gate-sim.js`]. 지금은 timeout 동안에도 덱을 숨기고(§8-1), 끝나면 `yes`로 돌아옵니다. 1-action-platformer는 10Mbps에서 장면 완성까지 45.2초라(§6-7) 이 경로가 실제로 쓰입니다. ④ `mount()`가 불릴 때까지 닫힌 작업을 하나 둡니다(custom의 React 경쟁, §9-5).
- `beforeprint`에서 lazy를 eager로 바꾸는 것만으로는 12장 중 6장만 인쇄됐습니다[print-engine §a]. 그래서 이 핸들러는 이번 인쇄를 안내 한 쪽으로 바꾸고, 다음 인쇄를 준비합니다. `beforeprint`에서 바꾼 속성이 그 인쇄에 반영되는지는 **미확인**입니다(R0). 그래서 이 핸들러를 timeout의 안전망으로 믿지 않고, timeout에서도 인쇄 CSS가 덱을 숨기게 했습니다.
- eager 조건을 기기로 정하므로, 창 크기를 바꿔 배율이 바뀌어도 게이트를 다시 돌릴 필요가 없습니다.
- JS가 아예 실행되지 않으면 속성이 붙지 않으므로 게이트도 걸리지 않습니다. 이 경우 장면이 그려지지 않으므로 인쇄할 내용도 없습니다.
- 비동기 렌더 전에 인쇄하면 원시 "PENDING"이 찍혔고, 게이트를 쓰면 안내 한 쪽만 나왔습니다(대화상자에서 확인)[print-engine 함정 17]. 장면 3개를 1.5초 뒤에 추가한 페이지는 게이트 없이 5/8쪽만 나왔습니다[spec-impact E9].
- 통합 게이트(`mount` 대기 포함)는 아직 시험하지 않았습니다. custom 프로토타입은 별도 `window.CUSTOM_READY = SceneKit.ready()`로 기다렸습니다[screen-ux §7]. R0·T7·T11에서 확인합니다(미확인).

**[PDF로 저장] 버튼**: `await` 준비 신호 `yes`(대기 중에는 진행 표시) → `window.print()`. 20초가 지나 `timeout`이면 "아직 다 그리지 못했습니다(이미지 n/m)" 경고와 함께 계속 기다리고, 학생이 원하면 **[그래도 인쇄]**(`PFScene.printAnyway()`)로 지금 상태를 인쇄합니다. 휴대폰·데이터 절약 모드(lazy 유지)에서 눌러도 먼저 lazy를 eager로 바꿔 이미지를 모두 받은 뒤 인쇄합니다(다만 휴대폰 인쇄는 보장 밖, §8-7).

### 8-4. 인쇄 범위 (project.html)

- 기본: 화면 그대로(요약 + 기술 문서 부록). 인쇄 쪽 수 = 화면 장면 수라서 학생 안내("장면 수와 쪽 수가 같으면 정상")가 단순합니다.
- HUD "요약만": `[data-pf-part="doc"]` 장면(기술 문서 부록과 P2 목차)에 `.pf-skip`을 붙입니다. 인쇄에서는 `display:none`이 되고, 쪽 나눔 선택자가 `.pf-skip`을 세지 않으므로 빈 쪽이 생기지 않습니다. 화면에는 계속 보입니다.
- **인쇄 집합이 바뀌면 번호를 다시 계산합니다**: 인쇄용 바닥글 번호(`.pf-n-print`, 예: 7쪽 PDF에서 "5 / 7"), 목차 쪽 번호, "→ p.n" 교차 참조를 인쇄되는 장면만 세어 다시 채웁니다. 인쇄 집합 밖을 가리키는 참조는 배포 주소의 URL 글자로 바꿉니다(§6-6). 화면 번호(`.pf-n-screen`)는 그대로입니다. 교차 참조는 긴 형태로 측정해 두었으므로(§4-3 원칙 1) 바꿔도 넘치지 않습니다. 이 다시 계산하기는 분할을 다시 하지 않으므로 게이트를 닫지 않습니다.
- 제출용 합본은 만들지 않습니다(【R0 결정】 Q3, §5-3). 학생은 프로젝트마다 이 페이지에서 따로 저장하고, 랜딩 `index.html`도 따로 저장합니다. 인쇄 범위 선택("전체 / 요약만")과 번호 다시 계산은 그대로 둡니다.

### 8-6. 실제 인쇄 대화상자 실측

Chrome 155에서 CSS로 쪽 크기를 정한 페이지를 "PDF로 저장"으로 열었을 때[print-engine §대화상자]:

| 항목 | 상태 |
|---|---|
| 용지 크기, 레이아웃(방향), 배율 | 숨겨지고 쓸 수 없음 |
| 여백 | 바꿀 수 있음. 고정 px 장면은 기본·없음 3쪽, 최소·맞춤 6쪽. **레시피 zoom-fit을 쓰면 4가지 모두 일치**(데모 7장면 → 7쪽) |
| 머리글·바닥글 | 여백이 최소·맞춤일 때만 나타나고 체크된 채로 나옴. 고해상도 미리보기에서 글자가 보이지 않았음 → 실제 PDF에 찍히는지는 미확인 |
| 배경 그래픽 | 기본으로 꺼짐 → 레시피가 `exact`로 대응 |
| 기본 대상 | 이 PC의 새 프로필에서 **"Microsoft Print to PDF"**(OS 기본 프린터가 기본 대상이 되는 것으로 추정). A4·배율·머리글이 켜지고 날짜·URL·"1/12"가 장면 위에 찍힘 |

- 근거 종류: 위 표는 모두 **데모 미리보기**(데모 7장면 페이지의 미리보기 쪽 수와 스크린샷)입니다.
- Edge 155는 UI가 다르지만 결과가 같습니다. "PDF로 저장"을 고르면 페이지·**시트당 페이지 수**·여백만 남고, 여백 기본·없음·최소 모두 "합계: 7 페이지"였습니다. 시트당 페이지 수를 1이 아닌 값으로 바꾸면 장면 여러 개가 한 쪽에 축소되어 들어가므로 학생 안내에 넣습니다(§8-8).
- Chrome은 이전에 쓴 대상·여백을 기억합니다. 학생이 예전에 바꾼 설정이 남아 있을 수 있습니다.
- 저장 버튼은 OS 저장 창으로 이어져 자동화하지 않았습니다. 대화상자 경로의 결과는 미리보기 쪽 수와 스크린샷 기준이며, **저장된 PDF 파일 자체는 미확인**입니다.

### 8-8. 학생용 인쇄 안내 (페이지 안 + README + format/06)

페이지 HUD의 [PDF로 저장] 옆 "?"와 `format/06`에 같은 문구를 둡니다. 화면에서만 보입니다.

> **PDF로 저장하기 — Windows PC의 Chrome·Edge에서 저장하세요**
> 1. **배포된 주소**(github.io)에서, 주소 끝에 `?style=`이 **없는** 상태로 페이지를 엽니다. 화면이 다 나타난 뒤 오른쪽의 **[PDF로 저장]** 버튼을 누릅니다. (Ctrl+P도 됩니다.) 프로젝트마다 상세 페이지에서 한 번씩 저장하고, 첫 페이지(랜딩)도 따로 저장합니다. 기술 문서 부록을 빼고 싶으면 저장 전에 HUD에서 **"요약만"**을 고릅니다.
> 2. **대상**에서 **"PDF로 저장"**을 고릅니다. 처음에는 컴퓨터의 기본 프린터(예: "Microsoft Print to PDF")가 골라져 있을 수 있습니다. 그대로 두면 A4로 바뀌고 날짜·주소가 찍힙니다.
> 3. **여백**은 **기본** 그대로 둡니다. Edge는 **시트당 페이지 수**도 1 그대로 둡니다. 용지 크기·배율 항목이 보이지 않는 것이 정상입니다. 배경 그래픽은 체크하지 않아도 됩니다.
> 4. 미리보기의 쪽 수가 버튼에 적힌 **"PDF n쪽"과 같으면** 저장합니다.
>
> Mac, 휴대폰·태블릿(iPhone·iPad의 Chrome·Edge 포함), Safari·Firefox는 지원 범위 밖입니다. Windows PC의 Chrome·Edge에서 저장하세요.

| 증상 | 원인 | 해결 |
|---|---|---|
| A4·세로로 나옴, 날짜·URL이 찍힘 | 대상이 Microsoft Print to PDF·프린터 | 대상: PDF로 저장 |
| 대상은 "PDF로 저장"인데 날짜·URL이 찍힘 | 여백이 최소·맞춤이고 "머리글 및 바닥글"이 체크됨 | 여백: 기본, 머리글 및 바닥글 체크 해제 |
| 쪽 수가 두 배쯤 많음 | 여백 최소·맞춤(구형 브라우저) | 여백: 기본 |
| 한 쪽에 장면이 여러 개 작게 들어감 | Edge 시트당 페이지 수가 1이 아님 | 시트당 페이지 수: 1 |
| "아직 페이지를 그리는 중입니다" 한 쪽만 나옴 | 준비 전에 인쇄함(느린 인터넷이면 20초 넘게 걸릴 수 있음) | 잠시 기다린 뒤 다시, 또는 [PDF로 저장] 버튼 |

| PDF 속 링크가 localhost를 가리킴 | 미리보기(로컬 서버)에서 저장함 | 배포된 주소에서 다시 저장 |
| 스타일이 내 설정과 다름 | 주소에 `?style=`이 붙은 채 저장함 | 주소에서 `?style=…`을 지우고 다시 저장 |
| Mac·Safari·Firefox·휴대폰에서 저장한 PDF의 크기·쪽 수가 다름 | 지원 범위 밖(확인하지 않은 환경) | Windows PC의 Chrome·Edge에서 다시 저장 |
| 쪽 수가 많아 부담됨 | 기술 문서 전문 포함 | 프로젝트마다 HUD "요약만"을 고르고 저장 |
| 모든 프로젝트를 한 파일로 내고 싶음 | 이 템플릿은 프로젝트별 PDF만 만듦(합본 없음) | 프로젝트마다 따로 저장해 여러 파일로 제출 |
| 장면 아래에 빨간 "내용이 잘렸습니다" 띠 | 소스 내용이 장면에 안 들어감 | 리포트의 "고칠 곳"대로 기술 문서를 줄이고 다시 빌드 |

- 학생 제출 PDF가 실패하는 주된 원인(기본 대상, 기억된 여백, 머리글)은 모두 대화상자에서 생깁니다. R0의 헤드리스 PDF 스파이크(§11-1)가 통과하면, 빌드의 선택 단계 "PDF 만들기(헤드리스 Edge)"가 프로젝트별·랜딩 PDF를 만드는 기본 경로가 되고 이 안내는 대체 경로로 내려갑니다. 이 경로도 Windows의 Edge를 쓰므로 Mac에는 해당하지 않습니다(Q1-b).

### 9-3. `<head>` 순서와 API

```html
<head>
  <meta charset="utf-8" /><meta name="viewport" content="width=device-width, initial-scale=1" />
  <script src="assets/scene-kit.js"></script>                  <!-- 동기, 가장 먼저: 준비 게이트 "no" -->
  <link rel="stylesheet" href="assets/scene-kit.css" />
  <link rel="stylesheet" href="assets/portfolio.css" />          <!-- 고정 렌더러만 -->
  <link id="pf-theme" rel="stylesheet" href="data/theme.css" />  <!-- 스타일 계약 [02 §1 T1] -->
</head>
```

- viewport는 위 한 줄 그대로 씁니다. **`user-scalable=no`·`maximum-scale`은 넣지 않습니다.** 휴대폰에서 축소된 장면을 손가락 확대로 읽는 것이 Q2 결정의 전제이기 때문입니다(§7-6). custom도 같습니다(§9-5).

| API | 설명 |
|---|---|
| `PFScene.track(promise)` | 비동기 작업 등록. 끝날 때까지 준비 게이트가 닫혀 있음 |
| `PFScene.ready` / `PFScene.whenReady()` | `"no"`·`"yes"`·`"timeout"` / 준비 Promise(`yes`에서만 풀림) |
| `PFScene.mount({ deck: '#deck', hud: true, scope: true })` | 장면 id·`aria-labelledby` 부여, 바닥글의 화면·인쇄 번호 채움, HUD·키보드·배율 계산 시작. 데이터 렌더 후 한 번. **mount가 불리기 전에는 게이트가 열리지 않습니다**(§8-2) |
| `PFScene.flow({ source, scene, items })` 🆕 | **측정 기반 컬렉션 분할**(설계안, 미검증). 1차 렌더에서 반복 항목을 `source`(측정용 장면 안의 `data-pf-flow` 컨테이너)에 모두 그리면, 키트가 측정용 장면(1280×720, k=1)에서 항목 높이와 장면 용량을 재고 장면별 묶음(인덱스 배열, 예: `[[0,1],[2,3],[4]]`)을 돌려줍니다. 2차 렌더에서 그 묶음대로 장면을 만듭니다(React가 DOM을 계속 소유하므로 재조정 충돌이 없음). 한 항목이 빈 장면보다 크면 §4-3 원칙 5 순서(축소 → 잘림 띠)를 따릅니다. `track()`으로 감싸 게이트에 등록됩니다 |
| `PFScene.fetchData(url)` 🆕 | no-cache fetch + `track` 등록. `?pf-stress=1`이면 배열 2배·문장 1.5배로 늘린 사본(custom 완료 조건 시험용, §9-5) |
| `PFScene.go(i)` | 장면 이동(§7-4) |
| `PFScene.print()` / `printAnyway()` | 준비 대기 → `window.print()` / timeout일 때 지금 상태로 인쇄(§8-2) |
| `PFScene.renderMermaid(nodes, config)` | 측정용 컨테이너에서 `mermaid.render()`로 차례대로 그림 |
| `PFScene.audit()` | 장면 상자 ≠ 1280×720, `scrollHeight` > 본문, 장면 밖으로 나간 자손, 장면 안 `fixed`·`sticky`, 장면 사이 이물질, 미완료·lazy 이미지, 열린 dialog, 잘림 띠, **인쇄 매체에서 글자·이미지가 있는 요소의 opacity < 0.05 또는 visibility hidden**(기본 숨김 등장 효과. `data-pf-allow-hidden` 예외), 장면 안 CSS `background-image: url()` → 문제 목록 |
| `PFScene.selfTest()` | 숨은 iframe 3개(1280×752, 1700×752, 1280×1000 — 모두 k=1)에서 장면 안 요소의 논리 좌표를 비교 → vw·vh·뷰포트 `@media` 의존을 찾아냄. 처음에 k가 다른 크기로 비교했을 때는 정상 페이지에서도 244개 중 47건이 잡혔습니다(줄바꿈 차이)[screen-ux §7]. 단계: R1.5(R1-core에는 없음, Q16) |
| `?pf-audit=1` 🆕 | 준비가 `yes`(또는 `timeout`)가 되면 `{ready, scenes, printScenes, audit, selfTest}` JSON을 base64로 `<pre id="pf-audit">`에 씁니다. 브라우저 창 도구가 없는 CLI 환경에서 Claude가 헤드리스 `--dump-dom`으로 읽는 통로입니다(§9-5 규칙 7, §11-1). `--dump-dom`이 비동기 준비를 기다리는지(`--virtual-time-budget`), 숨은 iframe의 `selfTest()`가 헤드리스에서 도는지는 미확인(R0) |

### 9-4. 장면 안 금지 목록 (고정 렌더러·custom 공통)

| 금지 | 이유 | 대신 |
|---|---|---|
| `vw`·`vh`·`dvh`, `h-screen`·`min-h-screen`·`w-screen`, `clamp(…vw…)` | 보는 사람의 창 크기에 따라 배치가 바뀜. 장면 안 `50vh`는 253px로 계산된 뒤 또 배율이 걸려 177.8px로 보였음 | 고정 px, em, 컨테이너 단위(`cqw`) |
| 뷰포트 `@media (max-width…)`, Tailwind `sm:`/`md:`/`lg:` | 뷰포트 기준으로 발동해 보는 사람의 창 크기에 따라 장면 배치가 바뀜(화면 ≠ PDF) | 컨테이너 쿼리, Tailwind `@md:`·`@3xl:`(`?plugins=container-queries`) |
| `position: fixed`·`sticky` | 모든 쪽에 반복 인쇄, 내용을 밀어냄 | 장면 안 `absolute` |
| 장면 안 `<dialog>`·라이트박스 | 배율만큼 작아짐 | body 바로 아래 |
| 장면 사이의 다른 요소 | 빈 쪽 | 장면 안으로 |
| `overflow: auto`·`scroll` 상자 | 인쇄하면 넘친 부분이 스크롤바 없이 잘림 | 분할 또는 줄 바꿈 |
| `content-visibility: auto` | 접근성 트리에서 빠짐 | 쓰지 않음 |
| 처음에 숨겨 두는 등장 효과(Tailwind `opacity-0` + `animate-…` 포함) | PDF에서 빠질 위험. 키트가 애니메이션 시간을 0으로 만들어도 `forwards`가 없으면 숨김으로 남음 | `data-pf-reveal`(화면 전용, 인쇄에서 강제 표시). `audit()`가 인쇄 매체의 투명 요소를 잡음 |
| 장면 안 CSS `background-image: url()`(표지 그림 포함) | 준비 게이트가 `<img>`만 기다려서, 덜 받은 그림이 인쇄될 수 있음 | `<img style="object-fit:cover">` |
| 반복 데이터를 생성 시점에 정한 개수로 장면에 나눠 담기(`chunk(a, n)`) | 다시 빌드해 글·항목이 늘면 넘쳐 PDF에서 사라짐 | `PFScene.flow`(§9-3) |
| 글자 하한 아래로 내리는 것 — **본문 14px · 코드 12px · 라벨 11px 미만** 【G5 결정】(옛 문구 "13px 미만 글자") | 노트북 k=0.835에서 라벨 11px은 약 9.2px이라 이보다 작으면 읽히지 않음. 축소도 이 하한에서 멈추고(`font-floor` 참고 지표), 그래도 넘치면 잘림 띠 | 타입 스케일(§2-2). 기본값은 그대로 13px 이상으로 쓰고, 하한은 축소가 닿는 바닥일 뿐임 |

### 9-5. `/portfolio-custom` 규칙 (SKILL.md·format/05에 넣을 문구)

custom 장면 규칙 전체는 아직 열린 질문 Q11의 추천안입니다. 다만 좁은 화면 처리(규칙 7의 375px 조건)는 Q2 결정(장면 축소 단일 모드)에 맞춰 바꿨습니다.

1. `../assets/scene-kit.css`·`../assets/scene-kit.js`와 `../data/theme.css`(프리셋이면 `../styles/<slug>/theme.css`)를 싣습니다. 키트는 렌더러 소유이며 고치지 않습니다.
2. 구조는 `<main class="pf-deck">` 바로 아래 `<section class="pf-scene">`만 둡니다. 장면 안 디자인은 자유입니다. 바닥글 "이름 · n / N"은 남깁니다.
3. §9-4 금지 목록을 지킵니다. Tailwind는 버전 고정 URL `https://cdn.tailwindcss.com/3.4.16?plugins=container-queries`만 씁니다(지금 custom `SKILL.md:25`의 버전 없는 `https://cdn.tailwindcss.com`을 교체). viewport는 §9-3의 한 줄을 그대로 쓰고 `user-scalable=no`·`maximum-scale`을 넣지 않습니다. 좁은 화면용 배치를 따로 만들지 않습니다(키트가 장면을 통째로 축소).
4. **반복 데이터는 `PFScene.flow`로만 장면에 나눕니다**(프로젝트·핵심 구현·이슈·기술·스크린샷 등). 장면당 개수를 코드에 박지 않습니다. 데이터를 받는 fetch부터 렌더 완료까지를 `PFScene.track()`으로 등록하고, 2차 렌더 뒤 `useEffect`에서 `PFScene.mount()`를 한 번 호출합니다. 게이트는 mount가 불릴 때까지 닫혀 있으므로 React commit 전에 인쇄 가능 상태가 되지 않습니다.
   ```jsx
   const [plan, setPlan] = useState(null);                       // 장면별 항목 묶음
   useEffect(() => { if (pf) PFScene.track(PFScene.flow({ source: '#flow-projects', scene: '#tpl-projects',
                         items: pf.projects.length }).then(setPlan)); }, [pf]);   // 1차: 측정용 장면에 전부 그림
   useEffect(() => { if (plan) PFScene.mount({ deck: '#deck' }); }, [plan]);     // 2차 렌더 뒤 한 번
   return <>
     {pf && !plan && <div className="pf-measure">                   {/* 1차: 측정용(보이지 않음, k=1) */}
       <section id="tpl-projects" className="pf-scene px-16 py-12">
         <div id="flow-projects" data-pf-flow className="grid grid-cols-1 @3xl:grid-cols-2 gap-8">
           {pf.projects.map((p, j) => <ProjectCard key={j} p={p} />)}</div></section></div>}
     <main className="pf-deck" id="deck">                           {/* 2차: 묶음대로 장면 */}
       {(plan || []).map((idx, i) => (
         <section key={i} className="pf-scene px-16 py-12"><div className="grid grid-cols-1 @3xl:grid-cols-2 gap-8">
           {idx.map((j) => <ProjectCard key={j} p={pf.projects[j]} />)}</div></section>))}
     </main></>;
   ```
   data는 `PFScene.fetchData('../data/portfolio.json')`로 읽습니다(no-cache fetch + `track` 등록). 주소에 `?pf-stress=1`이 있으면 키트가 배열 항목을 2배로, 문장 필드를 1.5배로 늘린 사본을 돌려줘 규칙 7의 "데이터를 늘린 시험"에 씁니다.
   Tailwind Play CDN이 스타일을 비동기로 만드는 시점과 측정 순서는 미확인입니다. R0에서 확인하고, 필요하면 flow가 측정 전에 두 번 tick을 기다리게 합니다.
5. 색·반경·글꼴은 fallback이 있는 CSS 변수로만 참조합니다[02 §8-6]. 장면 배경은 키트가 `var(--bg)`로 칠하므로 따로 하드코딩하지 않습니다.
6. 기술 문서 전문은 복사하지 않고 `../project.html?p=<폴더명>`으로 링크합니다(지금 규칙 그대로).
7. **완료 조건**(Claude가 통과할 때까지 반복 수정): `PFScene.audit()`가 `[]`, `PFScene.selfTest().diffs`가 0(R1.5부터. R1-core에서는 금지 목록·`audit()`·375px와 1280px 두 뷰포트 비교로 대신함[02 §11]), **375px 뷰포트에서 축소된 장면의 가로 넘침 0**(문서 폭 ≤ 뷰포트 폭), **데이터를 늘린 시험**(`?pf-stress=1`: 각 배열 항목 2배, 문장 필드 1.5배)에서도 `audit()` `[]`. 헤드리스를 쓸 수 있으면 "장면 수 = 쪽 수, 모든 쪽 960×540pt"도 확인합니다(Q11).

8. `format/05` 예시 프롬프트의 "스크롤하면 프로젝트 카드가 하나씩 나타나게"는 "화면에서는 카드가 부드럽게 나타나게(인쇄에는 모두 보임)"로 바꿉니다.

AI가 자유롭게 만든 결과물은 실행마다 달라서, 키트와 자체 검사 없이는 R-B를 보장할 수 없습니다[scene-design §8-7]. 그래서 규칙 4·7은 선택이 아니라 필수입니다.

### 10-2. 기동 순서

```text
<head>  scene-kit.js(게이트 "no") → scene-kit.css → portfolio.css → data/theme.css
PFScene.track(renderAll()):
  1. portfolio.json(no-cache) → applyStyle(가드·변형 키워드)        [02 §8-2]
  2. 글꼴 load(각각 catch) → fonts.ready(상한 8초)
  3. 요약 장면: 템플릿 + 변형 선택기(측정용 컨테이너)
  4. (project) md fetch → marked → Mermaid render → hljs → 정규화 → 분할 → 목차 번호·교차 참조 채움
  5. 덱에 붙임 → PFScene.mount(): id·aria·바닥글 화면/인쇄 번호·HUD·배율(모드 판단 없음), 키트의 "mount 대기" 작업 해제
  6. 해시 딥 링크 이동
게이트: (모든 track 작업 + mount) → (데스크톱 기기) lazy → eager → 이미지 load → fonts.ready(3초) → "yes"
        20초가 지나면 "timeout"(덱 숨김 유지 + HUD 경고·[그래도 인쇄]), 끝나면 "yes"로 회복
이후: loadingdone·?style= 교체·넘침 감시 → PFScene.track(repaginate()) / 인쇄 범위 변경 → 번호만 다시 계산
```

### 11-3. 기준선 B0 (기존 "픽셀 diff 0"을 대신함)

- 구성: 장면별 PNG(1280×720, DPR 1·2), 장면 나눔 JSON(구조 서명 + 보이는 글자 서명), PDF 단언 결과(쪽 수·크기·빈 쪽·잘림 0).
- 대상: 샘플 4편 상세, 랜딩, 상태 화면(`?p=` 없음, 문서 실패, 데이터 없음, 라이트박스). deck은 Q3 결정으로 없습니다.
- 채택 경로(Q16: R1-core → R1.5)에서는 R1-core에 서명 JSON + PDF 단언만 두고, 장면 PNG를 더한 B0는 **R1.5 릴리스 시점에 동결**합니다[02 §11]. 이후 모든 렌더러 변경과 스타일 컴파일러 회귀는 B0와 비교합니다[spec-impact §5].
- **유지 비용 정책**: Chromium 메이저는 약 4주마다 바뀌므로 "메이저마다 다시 기록"은 매달 하는 일이 됩니다. 그래서 메이저가 바뀌면 **서명 JSON과 PDF 단언만 자동으로 비교**하고, 달라졌을 때만 차이를 기록한 뒤 다시 기록합니다. 장면 PNG 비교는 렌더러를 바꿀 때만 합니다(줄바꿈 드리프트 자체는 미확인).

### 11-4. 하네스가 막지 못하는 것

- CDP로는 대화상자 여백 덮어쓰기와 lazy 이미지 차이를 재현할 수 없습니다. lazy는 T1에서 실패로 처리하고, 여백은 T12(사람)로 확인합니다[print-engine §c].
- `::marker` 넘침(§6-9), GIF의 인쇄 프레임, 실제 화면 낭독기 동작은 검사하지 않습니다.

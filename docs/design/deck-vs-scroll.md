# 스크롤형 vs 슬라이드 덱형 — 샘플 비교·평가

포트폴리오 페이지의 넘기는 방식을 "휠로 내리는 스크롤형"에서 "한 장씩 넘기는 발표 슬라이드 덱형"으로 바꾸면 어떤지 판단하시도록 만든 비교 문서입니다. 가이드 발표 덱 46장(https://koohoo-dev.github.io/portfolio-guide/slides/deck.html `#1`~`#46`)을 참고해 덱 샘플(B)을 만들었고, 지금 형식들과 같은 내용·같은 잣대로 쟀습니다. **어느 방향으로 갈지는 유지관리자께서 정하십니다.** 이 문서의 추천(§6)은 판단 재료입니다.

**비교한 형식 넷**

| 이름 | 무엇 | 위치 |
|---|---|---|
| **A0** | 지금 배포 중인 렌더러. 긴 스크롤 문서 | 레포 루트 `index.html`, `project.html`, `assets/` |
| **A1** | R0 통합 시험대. 1280×720 장면을 세로로 쌓아 휠로 스크롤(승인된 16:9 설계) | `spikes/r0/pages/` |
| **B 덱** | 이번 샘플의 기본 보기. 같은 장면을 한 번에 한 장씩 넘김 | `spikes/deck/pages/` |
| **B 스크롤** | 같은 샘플을 `?view=scroll`로 연 것. 같은 테마·같은 DOM으로 A1처럼 스크롤 | `spikes/deck/pages/…?view=scroll` |

- 내용은 넷 모두 같은 원천(`data/portfolio.json`, `data/projects/*.json`, `src/<id>/` 기술 문서)입니다. B는 새 문장·수치를 만들지 않았고, 장면 이름·라벨 같은 UI 글자만 더했습니다. 기술 문서 글자 수는 원문과 같습니다(13,661 / 25,761 / 28,226자).
- 프로젝트는 `0-Tidy-Mommy`, `1-action-platformer`(Switch Strike), `2-Yggdrasil` 셋입니다(`00-example-crafting` 제외). 측정은 주로 Switch Strike로 했습니다.

**샘플 여는 법** (자세한 조작은 `spikes/deck/README.md`)

```powershell
# 레포 루트(C:\Users\user\portfolio-test)에서
python -m http.server 4600 --bind 127.0.0.1
```

- 랜딩 덱: http://127.0.0.1:4600/spikes/deck/pages/index.html
- 프로젝트 덱: http://127.0.0.1:4600/spikes/deck/pages/project.html?p=1-action-platformer (`0-Tidy-Mommy`, `2-Yggdrasil`도 같음)
- 스크롤 보기: 주소 끝에 `&view=scroll`. 덱 보기에서 휠로 넘기기: `&wheel=1`(기본은 꺼짐)
- A1과 나란히: http://127.0.0.1:4600/spikes/r0/pages/project.html?p=1-action-platformer

**실험 환경**

- Windows 11, Node v24, Python 3.12 + PyMuPDF
- Chrome 155.0.8059.85, Edge 155.0.4283.62. 모두 헤드리스로 띄우고 CDP 파이프로 조종했습니다. 브라우저 프로필은 `%TEMP%\deck-*`에 만들고 지웠습니다.
- 서버: 자체 점검 127.0.0.1:4642, 비교 측정 127.0.0.1:4643(읽기 전용). 끝난 뒤 닫았습니다. 참고 덱은 라이브 주소를 바로 열었습니다(로컬 사본과 바이트까지 같음).
- PDF는 모두 CDP `Page.printToPDF`로 뽑았습니다. **실제 인쇄 대화상자의 "PDF로 저장"은 미확인**입니다.
- 화면 크기: FHD 1920×945, 노트북 1366×633, FHD@150%+즐겨찾기 막대(CSS 1280×556), 폰 375×812(터치 에뮬레이션), 확대 200%(에뮬레이션).
- 실제 휴대폰, 트랙패드, 실제 Ctrl+F·Ctrl+＋, NVDA·내레이터, 배포 주소(github.io)에서의 동작은 **미확인**입니다.

**근거 파일 위치** (전체 목록은 §8)

- 샘플 B: `spikes/deck/` — 설명 `README.md`, 자체 점검 `out/b-check.md`
- 비교 측정: `spikes/deck/out/compare/measure.md`(부록에 경로 168개 전체 표)
- 참고 덱 연구: `spikes/deck/out/ref/`
- `spikes/deck/out/`은 `.gitignore`에 들어 있어 **커밋되지 않습니다**(PNG·PDF가 무거움). 이 문서와 같은 PC에서만 열 수 있습니다. `spikes/deck/` 전체도 아직 커밋하지 않았습니다.

## 2. 참고 덱에서 가져온 것 / 가져오지 않은 것

참고 덱은 Chrome·Edge 모두 46쪽, 모든 쪽 960×540pt, 빈 쪽 0으로 R-B 조건을 통과했습니다(`out/ref/ref-booklet-bg-on-*.pdf`). 무대·HUD·주소·인쇄 방식은 그대로 쓸 만했고, 콘텐츠를 만드는 방식과 몇몇 버그는 쓸 수 없었습니다.

**가져온 것**

| 항목 | 참고 덱 | B |
|---|---|---|
| 무대·배율 | 1280×720 `.stage`를 `k = min(innerWidth/1280, (innerHeight−44)/720)`로 맞춤, 레터박스 | 같음(Q2 공식과 같음, 아래 44px는 HUD 자리) |
| HUD | 아래 44px 띠: ‹ ›, "03 / 46", 섹션명, 진행 막대 | 같음 + 개요·요약만·PDF로 저장·보기 전환 버튼 |
| 주소 | `#n`(1부터) | `#n` + `#s=<제목 id>`, A1의 `#s-n`도 받음 |
| 키 | →·Space·PageDown / ←·PageUp / Home·End | 같음 + ↑↓, Shift+Space, `O`(개요), `F`(전체 화면) |
| 시각 체계 | 인디고 색 토큰, 글자 단계(본문 15~16.5px 71%), 모티프(eyebrow/rlabel 머리, pill, banner, chip, card, note, callout, 라벨칩 → 설명, mini 표, dotrule, bignum) | 같은 체계를 포트폴리오 장면에 옮김(`pages/deck-theme.css`) |
| 레이아웃 | 16종 중 표지·목차·디바이더·카드 격자·그림 나란히·코드 + 주석·회고·mini 표 | Q7 순서에 맞춰 사용: 표지 → 목차 → 스크린샷 → 핵심 구현 → 이슈 해결 → 회고 → (디바이더) → 기술 문서 부록 |
| 인쇄 | `@page 1280px 720px` 여백 0, 장마다 쪽 나눔 | R0 인쇄 레시피 파일(`kit/scene-kit.css`)을 바이트까지 그대로 씀 |

**고쳐서 가져온 것** (참고 덱에서 확인한 문제)

| 참고 덱의 문제 | B에서 |
|---|---|
| 코드 블록이 가변폭 글꼴(Pretendard)로 그려지고 들여쓰기가 사라짐. 고정폭 글꼴은 굴림체로 대체 | D2Coding을 실제로 불러오고 `white-space: pre-wrap`. 코드는 Q8대로 "코드 위·'왜' 아래", 넘치면 장을 나눔 |
| React 18 + 브라우저 안 Babel(544.7KB), 버전 없는 CDN(`@babel/standalone`은 오늘 8.0.7로 해석) | 바닐라 JS, CDN 모두 버전 고정 |
| 덱 화면에서 Ctrl+P → 1쪽만, 글자가 22px 위로 밀림 | 덱·스크롤 어느 보기에서 인쇄해도 모든 장이 나오고 PDF가 쪽마다 같음 |
| 배경 그래픽을 끄면 디바이더·코드 바탕이 사라짐(잉크 72.6% → 1.9%) | `print-color-adjust: exact`. 배경 끔·켬 PDF 그림 차이 0 |
| 잘못된 hash(`#99`, `#abc`)면 주소와 화면이 어긋남, 키마다 방문 기록이 쌓임 | 잘못된 hash는 바로잡음, 목차·개요로 건너뛸 때만 기록 |
| 제목 태그 0개, 버튼 이름 `‹ ›`뿐, img alt 없음, `aria-live`·포커스 표시·줄인 움직임 없음, 대비 4.5:1 미만 글자 다수 | 제목 태그, 장면 이름, 버튼 `aria-label`, `aria-live`, `inert`, 포커스 표시, alt, `prefers-reduced-motion`, `--muted`·상태색 글자 대비 수정 |
| 터치 처리 없음(스와이프 무반응) | 탭 구역 + 가로 스와이프 |

**가져오지 않은 것**

- 강의 덱 전용 요소: 개념 상세의 비유, 나쁜 예·좋은 예 비교, 팁, 프롬프트 카드, 자가 점검 체크리스트, 치트시트, 색 견본, 어두운 경고 장, "복습본" 모드(B는 어느 보기에서든 바로 인쇄됨).
- **슬라이드마다 JSX를 손으로 쓰는 방식.** 템플릿은 `data/*.json`을 렌더러가 장면으로 바꿔야 합니다(CLAUDE.md 원칙 1 "지어내지 않는다", 렌더러 고정). 크래프팅 예제에 맞춘 하드코딩 코드 색칠 규칙도 쓸 수 없습니다.
- 46장에 디바이더 7장을 넣는 구성. B는 기본으로 부록 앞 1장만 넣었습니다(`?dividers=all|none`로 비교 가능).
- 슬라이드 평균 286자의 밀도. 복습본으로 읽는 용도의 밀도라 포트폴리오 요약 장면은 더 가볍게 했습니다.

**새로 넣은 것**(참고 덱에 없음): 개요 격자(`O`), 보기 전환 버튼, 장면 클릭 넘기기(왼쪽 30% = 이전), 휠 넘기기 옵션(`?wheel=1`), [PDF로 저장]·[요약만]. 이 중 **장면 클릭 넘기기는 결함 두 건(카드 그림 클릭, 더블클릭)의 원인**이라 다시 볼 대상입니다(§3).

## 3. 샘플 B 소개

**기능**

- 한 페이지 안에 두 보기가 있습니다. 덱 보기(기본)와 스크롤 보기는 같은 DOM이고 화면 CSS만 다릅니다. HUD 버튼이나 `?view=`로 바꿉니다.
- 이동: 키보드(→·Space·PageDown 등), HUD ‹ ›, 장면 클릭·탭(오른쪽 70% = 다음, 왼쪽 30% = 이전), 가로 스와이프, 개요 격자(`O`), 목차 링크, 휠(덱 보기는 `?wheel=1`일 때만, 몸짓 하나에 한 장).
- 주소: 덱 보기는 지금 장을 늘 `#n`으로 보여 줍니다. `#s=<제목 id>`로 기술 문서 제목에 바로 갑니다.
- 인쇄: R0 레시피 그대로. 장면 1개 = PDF 1쪽, 960×540pt. [요약만]은 부록·목차·디바이더를 뺍니다.
- 준비 게이트(`data-pf-ready`), 분할기(`pages/paginator.js`), 화면 감사(`audit()`)는 R0 것을 그대로 씁니다.
- 테마는 참고 덱의 인디고 체계로 고정입니다. **profile.md의 강조색(#2F6FEB)은 적용하지 않습니다.**

- **핵심 관찰:** 어느 보기에서 인쇄해도 같은 PDF이므로 덱 전환은 R-B를 낫게도 나쁘게도 하지 않습니다. 남는 기준은 화면 탐색·접근성·유지비뿐입니다.
- **선택 조건:** 덱을 기본으로 하려면 아홉 가지(§6 (나)의 조건 표)를 채워야 하고, Q2 문구("보기 하나")를 고치고 Q4 동기화 범위에 조작법을 넣어야 합니다.
- **이 심사의 추천:** 스크롤 기본 + 슬라이드(발표) 보기(§6 (다-1)). 기본 보기 하나만 R0 수준으로 검증하고 덱은 연기 시험으로 시작할 수 있어 1인 유지관리에 맞습니다.

### 5-4. 세 관점이 일치한 것

1. **덱의 이득은 요약 구간(약 10~12장) 이동과 면접 화면 공유에 몰려 있습니다.**
2. **덱의 손해는 기술 문서 부록(프로젝트당 39~68장)에 몰려 있습니다.** 찾기·전체 선택·낭독기가 지금 장에 갇힙니다.
3. **PDF는 형식과 무관합니다.**

5. **보기 좋아진 것은 테마 덕입니다.** 참고 덱 시각 체계를 쓸지는 형식과 따로 정할 안건입니다.
6. B에만 생긴 회귀(H3, PDF 링크, h1)와 공통 결함(연락처 링크, 복귀 링크, 클릭 삼켜짐)은 형식과 무관하게 고칩니다.
7. **지금처럼 토글로 두 보기를 "제공만" 하는 것은 비추천**입니다. 리크루터는 토글을 누르지 않으므로 사실상 기본값이 전부입니다.

### (다) 혼합안

**(다-1) 스크롤 장면 기본 + 덱 발표 보기** — 수강생·유지관리자 심사의 추천

- **내용:** 기본은 A1 탐색(장면 스크롤)입니다. HUD [발표] 버튼·`F` 키·`?view=deck`로 B의 덱 보기를 엽니다. 발표 범위는 기본으로 요약 구간이고, 부록은 원문 링크로 들어갔다가 뒤로 나옵니다. `Esc`를 누르면 같은 장의 스크롤 위치로 돌아옵니다. B 키트의 "한 DOM·두 보기" 구조를 그대로 가져옵니다.
- **바뀌는 것**
  - R1.5 "발표 모드"의 정의를 "전체 화면 + snap"(01 §7-5)에서 "B식 덱 보기"로 바꿉니다. 이미 로드맵에 있는 항목(`docs/design/README.md` R1.5 행)이라 결정 기록과 충돌하지 않습니다.
  - Q2 문구에 "발표 보기(같은 장면·같은 k 공식, 리플로 아님)"를 덧붙입니다. README 용어의 HUD에 [발표] 버튼을 넣습니다.
  - R1-core에서는 B 스크롤에서 이미 구현한 개선(지금 장 hash 추적, `aria-live`)과 HUD [목차] 버튼을 기본 보기에 넣습니다.
  - Q3·Q7·Q8·Q11은 그대로입니다. custom은 스크롤 계약만 따르면 됩니다(덱 보기를 custom에 열지는 나중에 정함).
- **비용:** R1-core +0~1일, R1.5 +2~4일(발표 모드 예산 안에서 개요·터치·hash로 키운 증가분). MVP 약 59~80일.
- **얻는 것:** 면접 화면 공유·발표의 덱 이득을 얻고, 기본 경로의 찾기·낭독기·휠 습관을 지킵니다. 덱 보기가 깨져도 기본 경로는 영향이 없습니다. 조건(위 표)을 채우면 나중에 **기본값 한 줄로 덱을 기본으로 뒤집을 수 있습니다.**
- **위험:** 리크루터가 처음 보는 것은 스크롤입니다. 덱의 요약 구간 탐색 이득(T1 5)을 기본 경로에서 놓칩니다. HUD [목차] 버튼과 클릭 삼켜짐 수정으로 상당 부분 따라잡을 것으로 보지만 **측정하지 않았습니다.** 그래서 R1-core 하네스에 "T1 ≤ 8걸음(A0 수준)"을 완료 기준으로 넣기를 권합니다.

**(다-2) 요약 구간은 덱, 부록은 스크롤** — 리크루터 심사의 추천

- **내용:** 표지~회고(10~12장)는 덱으로 보여 주고, 기술 문서 부록은 같은 테마의 스크롤 보기로 둡니다. 부록 디바이더의 "다음"이 스크롤 보기로 바꾸며 부록 첫 장으로 갑니다. HUD는 요약 기준으로 셉니다("08 / 12 · 부록 68장").
- **바뀌는 것:** Q7 순서는 그대로이지만 "구간마다 넘기는 방식이 다름"이라는 새 규칙이 생깁니다. Q3: [PDF로 저장]의 기본을 "요약만"(10~12쪽)으로 바꿀지 정해야 합니다(지금 결정은 "화면 그대로 = 요약 + 부록"이 기본). Q2 문구 수정, 01 §7-3~7-5 수정, 전환 지점의 "뒤로" 규칙 정의.
- **비용:** R1-core +4~8일(덱 탐색부 + 구간 전환 + 두 조작 규칙 시험).
- **얻는 것:** 내용 성격과 넘기는 방식이 맞습니다. 리크루터는 첫인상부터 덱 이득을 얻고, 부록에서는 찾기를 씁니다.
- **위험:** 한 페이지 안에서 조작 규칙이 바뀌어 헷갈릴 수 있습니다(실사용 미확인). 요약 구간은 덱이므로 위 조건 2·3·6·7은 여전히 필요합니다.

**(다-3) 폰 세로만 리플로** — 형식과 독립된 축

- 데스크톱·PDF는 16:9를 유지하고, 폭 768px 미만 세로 화면에서만 A0식 리플로를 씁니다. 폰 점수가 2~3에서 A0 수준(8)으로 오를 것으로 기대합니다(리크루터 심사 추정).
- **Q2 결정을 다시 여는 일**입니다. 비용은 Q2로 줄어든 옛 R1e 차이(원시 1~1.5일)에 버퍼·시험을 더해 약 +1.5~2.5일(추정)이고, 폰에서는 화면 ≠ PDF가 됩니다. (가)·(나)·(다-1)·(다-2) 어느 것과도 함께 쓸 수 있습니다. 결정 여부는 §7 질문 3입니다.

**비추천:** B를 지금 그대로(덱 기본 + 토글) 쓰는 것. 결함 14건이 기본 경로에 있고, 토글은 리크루터가 누르지 않습니다.

### 추천: (다-1) 스크롤 장면 기본 + 덱 발표 보기

이유는 다섯 가지입니다.

1. **인쇄 쪽 이득이 없습니다.** 덱을 기본으로 해도 R-B 결과는 같고, 화면 쪽 위험만 늘어납니다.
2. **덱의 이득은 발표 보기로 대부분 얻습니다.** 가장 큰 이득인 면접 화면 공유는 학생이 직접 덱을 켜는 상황이라 기본값일 필요가 없습니다.
3. **고장의 성격이 다릅니다.** 덱의 손실(찾기·낭독기·부록 넘기기)은 구조에서 오고 기본 경로에 두면 모든 방문자가 겪습니다. 스크롤 쪽 결함(클릭 삼켜짐)은 국소 버그입니다.
4. **일정이 거의 그대로입니다.** R1-core(학생에게 처음 닿는 5~6.5주)는 사실상 바뀌지 않고, 덱은 R1.5 발표 모드 예산 안에서 키웁니다. 조건을 채우면 기본값을 나중에 한 줄로 뒤집을 수 있어, 지금 덱 기본을 고르는 것보다 되돌리기 쉽습니다.
5. **세 심사 중 둘이 같은 결론**이고, 나머지 하나(리크루터)도 "B 덱 그대로"가 아니라 조건부·혼합안을 추천했습니다.

**이 추천이 놓치는 것도 분명합니다.** 처음 요청하신 방향은 "스크롤 대신 덱"이었고, 리크루터 첫인상에서는 덱이 실제로 빠릅니다(T1 5 vs 8 vs 22). **링크를 연 사람의 첫 경험을 덱으로 하는 것을 가장 중시하신다면 (나)보다 (다-2)가 증거에 맞습니다.** 어느 쪽이든 최종 결정은 유지관리자께서 하시고, 정해 주시면 결정 현황(README)과 01 문서에 반영할 변경 목록을 따로 만들겠습니다.
